# fetchloom

fetchloom puts the exact files a project needs into `data/`, pinned by SHA-256 in `data.lock`, from one shared cache. `data.toml` lists datasets and `data.lock` pins every file; both belong in git. `data/` does not.

## choose the command

| the task | run |
|---|---|
| a project needs a dataset | `fetchloom add <ref> --json` |
| a project needs several datasets from a list of links | `fetchloom add -i links.txt --json`: a dataset a line, `result.datasets` names them; a SHA-256 after a link checks its one file, and any failure writes nothing |
| a project needs files that are only on this machine | `fetchloom add ./folder --json`: they are copied into the cache and pinned by their bytes, with `ref = "local"` and no path; the folder is left as it was |
| a cloned project has data.toml but no data/ | `fetchloom sync --json` |
| one dataset, without downloading or changing the others | `fetchloom sync <name> --json`; `result.selected` echoes the names. the other datasets keep their data.lock entries and files, and the next plain `fetchloom sync` still checks them all |
| a script needs a dataset's path | `fetchloom path <name>`; stdout is the path, or `result.path` with `--json`, and it syncs that dataset alone first if needed. add `--locked` where data.lock must not change |
| scripts already read `data/train.csv` | set `path = "."` on the dataset in data.toml, then `fetchloom sync --json`: its files land straight in `data/`. datasets may share a folder unless two of their files land on one path, which exits 50 with `project.invalid` naming both |
| download once, no project files | `fetchloom get <ref> --dir <folder> --json` |
| webdataset `.tar` shards | add with `--no-extract`: `fetchloom add <ref> --no-extract --json`. loaders read shards packed, and unpacked they become one file per sample. to unpack them and keep only some files of every shard, one members table under a glob key chooses them, as `select = ["*.wav"]` under `[datasets.<name>.members."shard-*.tar"]` in data.toml, and shards pinned later follow it |
| one file at a path the user chose | `fetchloom get <url> -o <file> --json`; `result.file` is its absolute path. it needs one link to one file, else exit 2 naming `--dir`. `--sha256 <hex>` checks the file before it takes its name |
| several links, or a list of them | `fetchloom get <ref> <ref> --json` or `fetchloom get -i links.txt --json`; a SHA-256 after a link on its line checks its one file |
| words, not a reference | `fetchloom search <words> --json`, then use a `reference` from `result.candidates`. `--source hf,kaggle,zenodo` and `--limit <n>` narrow or widen it |
| restore a cloned project from a mirror of pinned files: a lab disk, a usb drive or a web server, as when a source is gone | `fetchloom sync --locked --mirror <folder or url> --json`; files not on the [mirror](https://github.com/nikhil-yn-aix/fetchloom/blob/main/docs/user/mirrors.md) come from their sources, and a folder mirror works with `--offline` |
| put a project's data on a lab disk or a usb drive, for others to sync from | `fetchloom push --to <folder> --json` copies the files sync places from this machine's cache into a folder [mirror](https://github.com/nikhil-yn-aix/fetchloom/blob/main/docs/user/commands/push.md); `result.copied` and `result.present` count the files, and `result.planned` those it set out to copy, which a push that stopped before writing copied none of; `--inputs <recipe>` adds what a recipe is made from, such as raw data with `place = false`. it downloads what the cache and the data folder lack first, mirrors before sources, but never builds: `offline.missing` naming a build means a recipe's result only `fetchloom build` makes, which needs the user's agreement; offline, run it again online |
| a project copied with its data folder to another machine or cache | run `push`, `build` or `sync` there as usual, `--offline` included: each pinned file the cache lacks is copied in from the data folder, where data.lock places it, once its SHA-256 matches the pin, with no request; `work.data_folder_objects` counts them. an edited file is never taken or changed, so the run then fails or downloads as it would without it |
| check data/ against the lock | `fetchloom status --json`, which trusts a placed file whose size and time are unchanged; `--verify` hashes every one. `fetchloom sync --verify --json` also puts back those whose bytes changed |
| code that writes results, edits inputs or wants another layout | write results outside `data/`: sync keeps files written inside it, but `status` lists them as extra. for edits, set `copy = true` on the dataset in data.toml, then `fetchloom sync --json`, which places writable copies; never change permissions of placed files, which can be hardlinks shared with other projects. an edit never reaches a recipe's step, which reads the pinned bytes: a fix a build should use goes in a step, or in a copy outside `data/` added as a dataset of its own. `path` in data.toml moves a dataset's folder. [working with raw data](https://github.com/nikhil-yn-aix/fetchloom/blob/main/docs/user/raw-data.md) shows each case |
| replace curl, wget, gdown, zenodo_get, kaggle, `hf download`, `aws s3 cp`, dvc import-url or pooch downloads | `fetchloom add <ref> --json` with the reference [other tools](https://github.com/nikhil-yn-aix/fetchloom/blob/main/docs/user/other-tools.md) maps each to; a `SHA256SUMS` file or pooch registry becomes an `add -i` list of link and SHA-256 lines |
| leave bad samples or unwanted files out of a dataset for good | `fetchloom drop <path>... --dry-run --json` first, then without `--dry-run`: paths are files or folders in data/, taken as written and never as patterns, and for a dataset with `place = false` the paths its files would have there. `result.dropped` names each file, its dataset, the archive it is inside and the pattern written to data.toml; tell the user to commit data.toml, and data.lock when `result.lock_changed`; when a recipe is made from that dataset, data.lock still pins its result made with those files, so tell them `fetchloom build <recipe>` comes first. it asks no server. a hand-written `exclude` does not reach files inside an archive; drop writes the archive's members table instead, and for an archive a glob key's table covers, a table of its own copied from the glob's, as `result.copied` lists |
| inspect signed-in accounts | `fetchloom auth --json`. signing in and out is the user's: `fetchloom auth login <source>` and `fetchloom auth logout <source>` in their terminal, with `--host` for a dataverse site; `--with-token` reads the key from stdin, for their scripts and CI |
| why a run uses some cache, mirror or limit | `fetchloom settings --json`: each setting's value and where it came from: a variable, the settings file, this machine or the default; give the run's `--mirror` too, and `mirrors` lists its mirrors first |
| check cached bytes | `fetchloom cache verify --json` |
| how much room the cache takes, or what `cache gc` would free | `fetchloom cache --json`. tell the user `result.freeable`, what `cache gc` frees now, never `bytes`: `linked` bytes are also files in their projects, so deleting them frees nothing, and `unneeded` bytes younger than a day or linked from a `get` folder stay too. `copies` are files of their own in projects that hold cached bytes; `cloned` of them are clones, which share blocks with the cache, so `copies - cloned` is what takes room twice. `unlinked_copies` lost their link when a project was copied without keeping links, as `rsync -a` without -H does. relinking means deleting a data folder, so leave that to the user. `fetchloom cache gc --dry-run --json` lists what gc would free; `--now` also frees what is less than a day old, so run it only with the user's agreement |
| free the disk raw data only builds read takes, such as data with `place = false` | first put it on a folder mirror: `fetchloom push --inputs <recipe> --to <folder> --json`. then `fetchloom cache gc --inputs --dry-run --mirror <folder> --json` reads each copy there and lists in `result.inputs` what gc would free, which mirrors it relies on and which recipes would fetch it back to run again, in `datasets[].costs.recipes`. show the user that and let them decide; only they say yes. it frees with `--yes` once they agree; without it, it exits 1 with `unconfirmed` and changes nothing. never pass a mirror the user did not name |
| git left `<<<<<<<` lines in data.toml or data.lock after a merge | `fetchloom lock --json`. it merges both files without downloading; when it exits 1 with `unconfirmed`, `result.merge.conflicts` names the datasets each side changed its own way, or one side removed while the other pinned other files for: ask the user which side to keep, then run `fetchloom lock --ours <name>` or `--theirs <name>`. in a rebase, ours is the branch rebased onto and theirs the user's commit |
| what the project uses | `fetchloom list --json`; `fetchloom list <name> --json` for one dataset, with `locked_files` paths, sizes, `sha256` and `url`, and `access`, what its source said about who may read it (`public`, `login`, `terms` or `unknown`) |
| a project with recipes, datasets data.toml makes with `from` and `run` | `fetchloom build --dry-run --json` says in `result.steps[].action` what the build would do with each step: `would_run`, `would_fetch`, `would_reuse` and `up_to_date` are what the build then reports, and `may_run` waits on a step before it. it shows each step's command in `result.steps[].run` and what it reads; show the user the commands of the steps that would or may run, as in a fresh clone, where every step whose pinned result no mirror holds runs. `fetchloom build --json` runs them, pins and places the results, and runs the project's code as the user, so run it only with their agreement. a plain `fetchloom sync` leaves out a pinned result no cache or mirror here holds and lists it in `result.placement.unbuilt`, and `status --json` in `result.unbuilt`. a warning `<name> changed since it was built` from sync or path means the placed result is data.lock's older pin; tell the user. `place = false` on a dataset only recipes read keeps it pinned and cached but out of `data/`: `status` lists it in `result.unplaced`, `list` gives `placed: false`, and `path` refuses it with exit 2 |
| a cluster job that builds without the network | on the login node, `fetchloom build --prepare --json` fetches everything the build reads and runs nothing; the job then runs `fetchloom --offline build --json` with the same recipe names, and `--check` when the prepare had it, with the user's agreement as for any build |
| reproduce a project's recipes in CI, or check that committed results still hold | `fetchloom build --locked --check --json` runs every step again from the pinned inputs and compares with data.lock, changing neither it nor data/; it runs the project's code, so only on branches the user trusts. exit 0 means every step made what data.lock pins; `build.differs` names the files in `result.steps[].check`; `lock.outdated`, exit 1, means data.lock does not pin what data.toml asks |
| checksums for an audit, or links for another downloader | `fetchloom export --json`: `result.placed` (files in data/, archive members included, with `sha256`) and `result.sources` (downloaded files with `url` and `sha256`, and imported ones, whose `url` is null). `fetchloom export -o data.sha256` writes `sha256sum -c` lines, `--format links` or `--format aria2` the links; a file already at the `-o` path is kept unless `--force`, which needs the user's agreement. a text form is complete or refused, but the link forms leave out recipes' results and files imported from a folder, which have no link, and `sha256` datasets with `place = false`, each with a warning and still exit 0; JSON names what is unknown or has no link in `unlocked`, `not_unpacked` and `no_link`, and what the form leaves out in `left_out` |

`<ref>` is a link, a DOI or an id: `hf:datasets/org/name`, `kaggle:owner/name`, `kaggle:competitions/slug`, `zenodo:3608990`, `figshare:34744689`, `osf:3eunr`, `dataverse:host/doi:10.7910/DVN/X`, `s3://bucket/prefix/`, `s3:https://host:port/bucket/prefix/` for another S3 service, `gs://bucket/prefix/`, `doi:10.5281/zenodo.3608990` or an https URL. with `add` and `get`, `--select "**/*.csv"` and `--exclude` keep only some files, and `--no-extract` keeps archives packed.

## rules that keep a run safe

- write `fetchloom`, never `fl`, in the commands, scripts and docs you produce. `fl` is a short name some installs give a person; on another machine it is missing or another program, such as powershell's alias for `Format-List`.
- pass `--json`. stdout is then one JSON document, with no colors and no questions, whatever the terminal. `-q`, `-v` and `--color` change only what a person reads on stderr. `--progress` keeps a plain progress line there now and then during a long download, for a user watching; never parse it.
- project commands look for `data.toml` from the current folder up to the top of its git repository, never above it. to use a project above the repository, name its folder with `-C <folder>`.
- plain words given to `add` or `get` are a search. without a terminal fetchloom does not guess: it exits 10 with `reference.ambiguous` and lists `result.candidates`. pick one and run again with its `reference`.
- a path such as `./x.csv`, `~/x` or `file:///x` is never searched or sent anywhere. `add` imports what it names, and `get` exits 10 with `reference.invalid`; plain words that name a file or folder in the current folder exit 2 with `usage`, so write them as `./name`. prefer the link, DOI or id where the data is published when there is one, since only that lets a teammate download it.
- a clone whose data.lock pins an import that neither the cache, the data folder nor a mirror holds exits 10 with `reference.unresolved`, naming the files in `details`, or 20 as a missing download does offline and in mirror-only mode. ask the user where those files are, then run `fetchloom add <folder> --as <name> --json`, which checks them against data.lock and changes neither file; other files exit 50 and change nothing. `lock --upgrade` never changes an import.
- a download over 1 GiB, or the size the user set in `FETCHLOOM_ASK_ABOVE`, stops with exit 1 and `unconfirmed`. ask the user before adding `--yes`; it approves the size, never a choice of dataset. do not raise `FETCHLOOM_ASK_ABOVE` to avoid asking.
- a server on this machine or its local network that only data.toml, data.lock or a `get -i` list names is refused with `network.refused`, exit 20, quoting the `allowed_origins` value that would let it through, with `fix` null. a link typed on the command line or a mirror the user named reaches its own origin alone, for that run, and an `add` of a link on a private address ends with the same quoted value in a hint: another port or scheme of that host is refused the same way, with a detail naming the trusted origin. do not set `FETCHLOOM_ALLOWED_ORIGINS` or that setting yourself; ask the user whether they trust that server.
- a private S3 bucket is read with the user's AWS keys only when the `s3_buckets` setting lists it; otherwise it exits 40 with `auth.required`, naming the setting. do not set `FETCHLOOM_S3_BUCKETS` or that setting yourself; ask the user whether they trust that bucket with their keys. an AWS profile that signs in through a role or IAM identity center also exits 40, with the command that exports its keys in `help`.
- mirror-only mode, the `mirrors_only` setting, refuses every request but to the mirrors, with `network.refused`, exit 20, naming the setting. never turn it off, or unset `FETCHLOOM_MIRRORS_ONLY`, yourself: it is the user's or their admin's rule. tell the user which files no mirror holds, from `errors[0].details`.
- `push` puts data where everyone who can read the folder can copy it. data whose source wanted an account or accepted terms, or did not say who may read it, exits 1 with `unconfirmed`, listing it in `result.asks`. ask the user whether everyone who can read that folder may have it before adding `--yes`, and never choose the folder yourself.
- to rename a dataset, change its table's name in data.toml and every recipe's `from` and `{name}` that read it; the next `fetchloom lock --json` keeps its pin under the new name without a request. `fetchloom remove` then `add --as` resolves it again and may pin newer data.
- commit `data.lock.d` with `data.lock`: a list there takes a new name when its files change, so `git commit -a` leaves it out and a clone then cannot read data.lock. a warning that git does not have a list in data.lock.d, from `status` or from the command that wrote it, means `git add data.lock.d` before committing. a `status` or `build` warning that git does not have a file of a recipe's code means the `git add` its help names, since a clone without it cannot build the recipe from the same code; one that `.gitignore` leaves out a code file is the user's choice to make. a clone that stops with `data.lock names data.lock.d/..., which is not there` needs the commit that adds it; never delete data.lock to get past it, since relocking pins newer data and drops every recipe's pin.
- never put a token in data.toml, code or a command you show. fetchloom reads keys the source's own tools saved; if none exists, ask the user to run `fetchloom auth login <source>` in their terminal.
- `get` checks every target in an output folder before removing earlier versions; a later conflict leaves earlier files in place.
- `get -o` leaves a file already at the path as it is: holding the same bytes it exits 0, holding others it exits 50 with `local.not_empty`. a rerun whose file still holds what the link served last asks the server only whether it changed, so an unchanged large file needs no `--yes`. `--force` replaces it; use it only with the user's agreement.
- `sync` keeps files a person edited and says so. `sync --force` replaces them; use it only with the user's agreement.
- an archive inside another archive lands packed, with a warning whose help unpacks it beside itself; show that command too.
- fetchloom leaves a `.rar` packed. its warning, in `warnings` with `--json`, names a command for this system that unpacks it into `<name>-unpacked` beside it, inside the data folder git ignores: unrar on linux, unar on macos, 7-Zip on windows. the program may need installing first, so show the command to the user rather than run it.
- an archive cut into parts, such as `scans.zip.001` to `.003` or `train.tar.gz.aa`, `.ab`, unpacks as one archive only when one dataset lists every part: add the folder, record or prefix that holds them all, not a link for each part. a warning names a missing part, rar volumes and zips spanned over `.z01` files stay packed with a next step, and members tables and `drop` name the archive by its first part.
- a file a person deleted from data/ comes back at the next sync, with a warning, and `result.placement.put_back` names it. never delete placed files to curate a dataset; `fetchloom drop <path>` leaves them out for good. drop refuses a file of a recipe's result, which the recipe's step chooses, and a dataset's only file, which `fetchloom remove` takes out with the dataset; the warning's help says which applies.
- `remove`, `drop` and `sync` delete only unchanged files fetchloom placed, and only inside the data folder. a warning names each folder they leave holding other files, and the old data folder once `data_dir` changes; tell the user instead of deleting those yourself.
- a file already at a pinned path that holds the pinned bytes is adopted: sync takes it as placed and, where the drive makes hardlinks, links it to the cache, which makes it read-only. `remove` later deletes it like any placed file and warns that it was already there.
- to preview `add`, `remove`, `drop`, `sync`, `lock`, `push` or `cache gc`, `cache gc --inputs` among them, add `--dry-run`. it does not apply project or cache changes; `result.changes` lists the paths. explicit `FETCHLOOM_TRACE` output is still written. a kaggle rules check can read its smallest file when its listed size is at most 4 MiB; wrappers can be larger, under the 64 MiB API-response limit, and none of those bytes is kept.
- in a container or a hosted notebook, the default cache can be read-only or lost with the session; [notebooks and containers](https://github.com/nikhil-yn-aix/fetchloom/blob/main/docs/user/notebooks.md) says where to set `FETCHLOOM_CACHE`.

## reading a failure

`errors[0].kind` names what went wrong. `errors[0].fix`, when present, is a runnable suggestion; check that it fits the user's intended inputs before running it.

`status` differences and sync conflicts still exit 0. inspect every status array and `result.placement.kept` before using inputs; a successful `path` is not proof that its bytes match the lock.

| exit | kinds | what to do |
|---|---|---|
| 1 | `unconfirmed`, `lock.outdated` | ask before `--yes`; after a git merge, ask which side of each dataset in `result.merge.conflicts` to keep; for `lock.outdated`, the lock is missing or differs from the manifest, so review the inputs before running `fetchloom lock`. a `--locked` run never offers a `fix` that would change data.lock: changing it is the user's call. a clone with no data.lock has nothing pinning its bytes: ask the user whether the project's owner can commit data.lock before `fetchloom lock` pins what the sources serve today |
| 2 | `usage` | fix the command line as `fix` or `help` says |
| 10 | `reference.*`, `source.invalid` | check the id or link; for `reference.ambiguous`, choose a candidate from `result.candidates` |
| 20 | `network.*`, `offline.missing` | retry later; to go online, remove `--offline` and unset `FETCHLOOM_OFFLINE` if it is `1` or `true` |
| 30 | `integrity.mismatch` | the bytes, size, archive tree or stated hash differ from the expected pin. check any supplied `--sha256` and the source; this does not prove upstream data changed. `cache verify` means cached bytes differ, possibly through a shared hardlink. preserve edits and ask before `sync --force` restores the pins. when a source now serves other bytes than data.lock pins, `fix` is null: never run `lock --upgrade` on your own. tell the user the two ways on, the pinned bytes from a folder mirror someone pushed them to (`fetchloom push --to <folder>`, then `fetchloom sync --mirror <folder>`), or `fetchloom lock --upgrade <name>` if the new bytes are intended |
| 40 | `auth.required` | ask the user to sign in in their own terminal with the command in `help`, to replace a refused key the message names by where it comes from, such as `HF_TOKEN`, or to accept terms at the page in `help` |
| 50 | `local.*`, `project.*` | a local I/O or resource failure, file conflict, or broken data.toml; report the cause. a link in data.lock that carries a login or a secret stops every command, with `fix` null: the user takes it out or restores data.lock from git, and you never repeat the link. `project.changed` means data.toml or data.lock changed while an add downloaded, so it wrote neither: check the change, then run the add again. an unfinished git merge conflict in data.toml or data.lock is for `fetchloom lock`, as `fix` says; it never picks a side, and neither may you: `--ours` and `--theirs` only with the user's choice. `data.lock pins <file> at N bytes, but its SHA-256 is that of M bytes` means data.lock was edited by hand or damaged: `fix` is null; ask the user to restore it, and never upgrade the dataset in its stead |
| 60 | `build.needed`, `build.failed`, `build.differs` | `build.needed`: a recipe changed or was never built since data.lock pinned it, or its pinned result is on no machine or mirror here; `details` say what moved. building runs the project's code, so `fix` is null: show the user `fetchloom build --dry-run --json` and build only with their agreement. `build.failed`: a step failed or wrote what a result cannot hold; read `errors[0].details`, the last lines of its output, and `.fetchloom/builds/<name>.log`. `build.differs`: a rebuild made other files than data.lock pins, which another version of a program or library can cause as well as randomness; report the files `errors[0].details` names and keep data.lock as it is. the rebuild is kept, and `status --json` lists it under `result.candidates`, each file that differs with `file`, the cache file of the rebuild's bytes, and `pinned`, data.lock's, for the user to compare; never run `fetchloom build --accept` without the user, since it chooses those files over the pinned ones |
| 130 | `interrupted` | the run was stopped; completed placements stay, unfinished copies are discarded; run it again |

`cache gc` failures retain successful counts and `result.not_removed`; `cache verify` uses `result.unreadable`. these entries contain `path`, `kind`, `os_code` and `message`. use the original cause before suggesting permission changes. unreadable cache change marks stop sync and get: repair storage or access, verify and retry; never delete the marks to bypass the refusal.

a reporting failure does not roll back command effects. JSON encoding failures and stdout errors other than a closed pipe use exit 50; inspect project status before retrying a command that changed it. failed add rollbacks name private recovery files under `.fetchloom/`; preserve those files and never paste their contents into logs.

`fetchloom completions <shell>` prints a script that completes commands in bash, zsh, fish, powershell or elvish; where it goes is the user's choice. `fetchloom help --json` lists every command and option, with each one's help.

## python

```python
import fetchloom
path = fetchloom.path("iris")  # syncs iris alone if needed and returns its folder
fetchloom.sync(names=["iris"])  # syncs iris alone and returns the project folder
iris = fetchloom.get("https://example.org/iris.csv", "iris.csv")  # one file, no project
```
