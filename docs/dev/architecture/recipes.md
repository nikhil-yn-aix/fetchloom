# recipes

a recipe makes a dataset from other datasets with a command a person writes in `data.toml`. this page covers what the code reads, how a result is keyed, how a stale pin is found, and how `fetchloom build` runs a step, takes in what it wrote, pins it and places it, checks a step against its pin, keeps a rebuild that differs and prepares a build for a machine without the network.

a dataset is fetched or made, so the manifest hands every caller an `Origin` to match on. code that only makes sense for a source, such as resolving a reference, drafting a pin or the spec hash, takes a `Source`, so the compiler finds each place a recipe must be left out. relocking asks nothing for a recipe, keeps its `Derived` pin while `data.toml` has the recipe and drops it with the recipe.

## reading data.toml

`Reader::recipe` refuses a recipe with `ref`, `select`, `exclude` or `extract`, one without `from` or `run`, and a `run` that is not a list of words: no shell ever reads it. each word goes through `Template::parse`, which splits it into text and `{name}` folders, reading `{{` and `}}` as braces of their own; the reader then checks that the words name every input and `{out}`, and nothing else. once every dataset is read, `recipe::order` runs Kahn's algorithm with a name-ordered queue over the `from` edges; a cycle comes back as its path, `a → b → a`, for the error. `code` paths get the same syntax checks as `path`, plus the files fetchloom writes, and a check against `data_dir` once it is known. `env` names must be portable and neither fetchloom's own nor named like a secret, and a message about `env` cites its line by number only, as one about `ref` does.

## the key

a result is named by its key, the SHA-256 of one line of JSON:

```text
{"scheme":"fetchloom-recipe-1","from":[[name, content], ...],"run":[word, ...],"code":[[path, "sha256:…" or "tree:sha256:…"], ...],"env":[[name, value], ...]}
```

`from` is sorted by name, `code` by path and `env` by name; `run` keeps the words as written. strings are escaped as `serde_json` and python's `json.dumps(obj, separators=(",", ":"), ensure_ascii=False)` escape them, and `a_known_key_matches_python` pins one key to the hash python gives, so a change to the scheme fails a test before it changes anyone's keys. a change to what enters a key, or how, takes a new scheme name.

`content` of a fetched input is the SHA-256 of one line a pinned file, sorted by path: `path \t size \t sha256`, or `path \t sha256:<tree>` for an archive that unpacks, whose own size and hash stay out, since the step finds its files and not it, so a source that packs the same files again keeps every key. the lines decide which files the step finds and where, since the layout of unpacked members follows from them, and they leave out links, MD5s, versions and times. the dataset's members tables, which choose the files inside its archives, add a line for each pattern after the files, `member \t <archive path> \t select or exclude \t <pattern>`, sorted by archive, then select before exclude, then pattern, each once, so a dataset without them keeps its content and how the patterns are written does not change it. `content` of a recipe's input is that recipe's pinned `tree`, so an upstream rebuild that gives the same files keeps every key after it, the early cutoff of build systems à la carte.

code is hashed by `code::hash`, which walks the path from the project root with `symlink_metadata` and refuses a link or a special file anywhere on the way. a file with no NUL in its first 8,000 bytes, git's text test, is hashed with each CRLF made LF while it streams, a CR held back until the next byte shows whether an LF follows; any other file is hashed as it is. a folder is the tree hash of its files, in the encoding of the cache's records of unpacked archives, with NFC paths and normalized sizes, leaving out version control folders, `__pycache__`, `.ipynb_checkpoints`, `.DS_Store` and `Thumbs.db`.

## finding a stale pin

`Step::read` takes a recipe as it stands: each input's pinned content, `run` as written, each code path's hash on disk and `env`. `Step::changes` compares it with the `Derived` pin and names what moved: no pin (`Unbuilt`), an input pinned to other content or not pinned yet, `run`, a code file changed or missing, `env`, or a key that disagrees though everything it records agrees. nothing moved means data.lock pins what building the recipe now would make.

`lock --check` and `sync --locked` turn changes into `build.needed`, exit 60, after any `lock.outdated` finding, since a build reads what `fetchloom lock` pins. `status` lists the recipe under `unlocked` with what moved, `sync` and `path` place the pinned result and warn through `tell_stale`, as [placing results](#placing-results) says, and `lock`, which keeps every recipe's pin, warns through it too and names the recipes it returns in its last line rather than calling data.lock up to date. the JSON `fix` of a build is always null: `output::fix` skips any command `cli::runs_code` says would run the project's code, so no script or agent runs a build unasked.

## trust

`data.toml` comes with whatever repository a person clones, so a recipe's command is untrusted until that person builds it. only `cli/build.rs` reaches `build::step::run`, and `no_other_command_runs_a_step` keeps every other command from running one: it gives a recipe a step that would leave a file behind and runs each command against it. `build --dry-run` shows the command before anything runs it, with `<build>` standing for the private folder a build makes in the cache, and decides each step as the build does, so a step the build would run, as one whose pinned result a fresh clone lacks, shows as one. there is no sandbox: a step runs as the person who builds, with their files and keys.

## deciding a step

a build takes the project's hold for its whole run, relocks the sources of the closure of the named recipes, `Scope::Only` of it, as a sync of them would, and keeps the new lock in memory. each recipe then, in closure order, gets its key from `Step::read` against that lock, so a result built earlier in the same run counts as its input's content:

| data.lock pins | the cache holds | action |
|---|---|---|
| this key | every file of its pin | `Up to date` |
| this key | not every file, but the data folder or a mirror holds the rest | `Fetched`: `fetch::mirrors::fill` copies them in, and nothing runs |
| another key or none | a whole record of this key, on unix written by this user and writable by no one else | `Reused`: the newest record is pinned |
| this key | not every file, and neither the data folder nor a mirror holds the rest | run; the same tree keeps the pin, another is `build.differs`, kept as [a rebuild that differs](#a-rebuild-that-differs) |
| another key or none | no whole record | run, and pin what it made |

`course` in `cli/build.rs` is this decision up to the mirrors: `Held`, `Lacking`, `Built` or `New`. the build, its [dry run](#the-dry-run), `room` and `--prepare` all take it, so they cannot tell the same step apart.

before a run or a reuse the build takes `Cache::hold_key`, an OS lock on `builds/<key>/lock`, and looks for a record again under it, so a second build of one key, in another clone sharing the cache, waits with `Waiting for another fetchloom building <name>` and reuses what the first made. a disk without locks lets them overlap, which costs only the second run.

## the dry run

`preview::foresee` walks the closure in build order without running, fetching or writing anything, and gives each step the action the build then reports: `course` on data.lock as the build would hold it at that step, with each result `Built` would reuse pinned in a copy, against `Ahead`, the cache with the objects the steps before would have put in it: the files `Loop::ready` lays out for the fetched datasets a step that runs reads, each archive it would download for them, and the pinned files a mirror gives or a step run again must make. `Lacking` is `would_fetch` when the data folder, as `DataFolder::holds` finds it where data.lock as the build holds it places each file, and then the folder mirrors, found by their marker as the build finds them with a plain file of the right size, hold every file the cache lacks, `may_run` when only a web mirror could give them, which a dry run never asks and an `--offline` build skips, and `would_run` otherwise. a step that reads a dataset the build pins anew, its entry moved past its pin or not pinned yet, or the result of a step that runs for a key data.lock does not pin, gets no key and `may_run`, since only that pin or result tells what it does; its line names what moved and the steps it waits on, or says it runs again only if their results change when its own pinned result is here. `tell` prints the command and what it reads under each step that would or may run. `a_dry_run_says_what_the_build_then_does` runs a dry run before each build of a chain of two recipes, in each state of the cache, and compares the actions.

## the room a build needs

before the first step runs, `Building::room` in `cli/build/room.rs` says what the steps that will run may take on the disk holding the cache. `running` decides them through `course` without asking a mirror, so it errs on more: every step for `--check`, else each whose pin does not answer its key, or whose files the cache lacks unless a whole record of its key would be reused, and each after one that runs. for each, `needs` adds the files of the fetched datasets it reads that the cache lacks, once a build, with what an archive unpacks to or its size again while that is unknown, what it reads in all, and its result as data.lock last pinned it. `space::peak` keeps every download and result, which stay in the cache, and adds the largest step's inputs only when a probe in a `Staging` folder finds that the disk does not clone files. when the peak and `build_floor` pass `space::free`, `cli::ask_room` asks, which `--yes` answers and `--json` turns into `unconfirmed`. the data folder's own disk, which a result copied there would also take room on, is not counted yet.

## the step

`Loop::ready` first puts in the cache every file of the fetched datasets the step reads: from the data folder's file where data.lock places it, once it hashes to the pin, as [copies from the data folder](cache.md#copies-from-the-data-folder) describes, else mirrors first, then sources, an archive unpacked again when a file it holds is missing. the step still reads only the cache's copies, so an edit in the data folder never reaches it. it plans them with `plan::inputs`, which lays out the datasets `place = false` keeps out of the placing plan too, so a build of a recipe made from one fetches it in a clone whose cache lacks it. `Staging` makes `tmp/<16 hex>.build` in the cache, 0700 on unix, and holds its `lock` as an archive's staging does, so `Cache::sweep_staging` clears a folder a killed build left once that lock is free, and dropping it clears the folder. an edit in the data folder never reaches a step: placing keeps it as `Reason::Changed`, and `tell::not_read` warns, for a kept file whose dataset a recipe reads, that the recipe reads the pinned bytes, with how to build from the fix, never `--force`, which would undo it. `inputs::make` places each dataset's files in `in/<name>` with `Placer::without_hardlinks`: reflinks where the disk clones, else copies, read-only, never flushed, since they are scratch. a fetched dataset's files are laid out by `plan::expand`, archives by what they unpacked to; a result's are the members of its pin.

`step::run` starts the words of `run`, each folder in place, with no shell, in the project folder, stdin null, the person's environment plus `env` and `FETCHLOOM_BUILDING`. std looks for a bare program name in fetchloom.exe's own folder and the windows folders before `PATH`, and adds `.exe` alone, so on windows `step::program::find` looks it up first as cmd.exe would: in the folders of the step's `PATH` in order, each with the `PATHEXT` extensions windows starts, a name with a folder in it from the project folder, and never the project folder itself. the full path goes to std, which still runs a `.bat` or `.cmd` program through cmd.exe with its own quoting and refuses an argument it cannot pass; a name not found goes to std as written. a fetchloom inside the step that would take that project's hold fails at once in `hold_until` with exit 2, since the build holds it. both pipes are read on threads into `.fetchloom/builds/<name>.log`, made anew with mode 0600 on unix, which drops its older half when it would pass 16 MiB, and into a 64 KiB tail whose last 20 lines go into a failure's details unless `Ran.told` says every line already reached the terminal as the step ran, so a person reads them once. the thread that watches the step hands each line to the terminal, dim, unless `-q` or `--json` asks for none, and looks at the child often at first, then every 200 ms, ending it when a stop is asked. it looks at `space::free` of the cache at once and then every 2 s, and ends the group with `Ended::Low` once less is free than `space::floor` of the `build_floor` setting, the larger of 1 GiB and 1% of `space::total` when unset; the build then fails with `local.io`, saying what `Staging::written` found in `out`.

`group::Group` holds the step's process with everything it starts. on unix it is a process group of its own, `process_group(0)`, so the terminal's ctrl-c reaches only fetchloom. the build ends the whole group with SIGKILL when a stop is asked and once the step exits, so nothing it left running writes while its result is taken in. a second ctrl-c calls `build::step::end_running`, which ends the group of every step still running, before fetchloom exits with 130. on unix a build also listens for SIGTERM, which schedulers send before their SIGKILL: `Terminate` asks the stop as a first ctrl-c does, then calls `end_running` at once, and a second SIGTERM quits as a second ctrl-c. a scheduler may send its SIGTERM to every process of a job, so a step that fails once a stop was asked counts as stopped, `Ended::or_stopped`; one that exited with 0 keeps its result. tokio keeps the handler once it is set, so only `build` sets one, and every other command still ends at SIGTERM's default. a process that calls `setsid` leaves the group and is not ended; its open output is waited for 2 s at most. on windows it is a job object from process-wrap, which takes in every process the step starts, and `Group::end` ends the job with `TerminateJobObject` where unix sends SIGKILL. only process-wrap's tokio wrapper with `KillOnDrop` gives the job its kill-on-close limit, so the step starts as tokio's child from the same std `Command`, and only calls that need no runtime touch it: `try_wait`, `start_kill`, and its pipes taken back as std files. fetchloom holds the job's last handle, so the job ends with fetchloom however it ends, and `end_running` has nothing left to do there. the console's ctrl-c reaches a windows step as it reaches fetchloom, and `Ended::or_stopped` counts the failure that follows as the stop.

## taking in a result

once the step exits with 0, the build hashes its code again and fails when a file changed, since the result would answer code that is no longer there. `capture::read` walks `out/` with each entry's own type, never following a link: a link, a device, a fifo or a socket is refused by its path, and so is a name that is not UTF-8. each path is made NFC, the form `data.lock` records, and refused when `name::escapes`, `name::metadata` or `name::unportable` refuses it; `name::unportable` applies windows' rules and the 255-byte name limit on every system, so a result made on linux places on windows. `name::fold` keys find two names one disk takes for one, by case or composition, and a file where another needs a folder. `most_files` bounds the count. each file is hashed on the placement threads, with its size, time, inode and ctime looked at before and after, and a file that moved is refused.

`capture::publish` then follows the cache's flush rule: up to 64 files are flushed one by one, more with one `Batch` flush where the kernel reports write-back errors. a file with one name that the user owns is sealed where it is, made read-only and dated by its birth, then hardlinked or renamed into `objects/` by the cache's own publication, and a new object must be the very inode that was hashed. any other file, and every file on windows, is copied into the cache with `Cache::copy_in`, which checks the bytes against the hash, so a step that linked a person's file into its result never makes it the cache's. each object the cache did not hold counts in `work.objects_written`, as a download's does. the result's record, `builds/<key>/<tree>`, is written last, durably, in the tree encoding of the records of unpacked archives.

## committing

the build writes `data.lock` and its parts once, after its last step, with `Loop::write_rendered`, only when the lock it made differs from the one it read; a pin keeps its `locked` time while its key and tree stay. a step that fails, is stopped or writes what a result cannot hold returns before that, so `data.lock`, `data.lock.d` and the data folder stay byte for byte as they were, while the results of the steps before it stay in the cache by key and a build run again reuses them. the errors are `build.failed`, with the exit code or signal and the tail, and `build.differs`, both exit 60, and the JSON `result` of the steps that finished stays beside them.

## checking

`build --check` and `build --locked` read data.lock as it is: `pinned_as_asked` runs the `--locked` check of `lock --check` over the closure first, turning a recipe's `build.needed` into `lock.outdated`, since they compare with pins or may not change them, and a dry run with `--locked` does the same. after the relock, a pin it changed anyway, as `repinned` finds a result dropped for a recipe data.toml no longer has, is `lock.outdated` too, before any step runs, so `--locked` never writes data.lock. it then runs `Building::check_step` for each recipe in closure order. a recipe input is its pinned result, fetched from a mirror when the cache lacks it, never the rebuild this check made of it, so every step is checked against data.lock alone; one whose input is nowhere is `skipped`. each step runs through `make` with its pinned tree as `expected`, so a rebuild that matches enters the cache with a record, as the pin's result, and one that differs is kept as below. a step that fails returns at once with the report so far; one that differs does not, and `build.differs` comes once every step ran. a check never writes data.lock, places nothing and takes no key lock: two checks of one key both run.

## preparing

`build --prepare` walks the closure as a build would decide it, without running anything: a step whose pin answers its key and reads no recipe that would run needs only its result, from the cache or `fetch::mirrors::fill`, which asks the data folder before the mirrors; every other step, and every step with `--check`, gets `Loop::ready` for the fetched datasets it reads and the mirrors for the pinned results of the recipes it reads that will not run. a step after one that would run counts as one that runs, since its key waits on that result. a build, not a check, then gets `Loop::prepare` for the fetched datasets in scope through `Building::ready_to_place`, since it places them once its steps are done and a dataset only a skipped step reads must be on the machine too. `Loop::write_lock` then writes the sources the relock pinned anew, so a later `--offline` build relocks nothing; the derived pins stay as they are, and nothing is placed.

## a rebuild that differs

a step run again for a key data.lock pins can make another tree. `compare::compare` merge-joins the pinned files and the rerun's by path into `matching`, `changed`, `missing` and `extra`, which the JSON step's `check` carries and the `build.differs` error lists, 20 paths a step at most. the rerun's files still enter the cache through `capture::publish`, but `Cache::record_result` is skipped: a record under `builds/<key>` is what a later build reuses, and a rebuild no person chose must never become a pin that way.

instead `State.candidates` in `.fetchloom/state` keeps a `Candidate` for the recipe, its key, its tree, the tree data.lock pinned beside it and its files, replacing any kept before. keeping one registers the project with the cache, since a failed build never reaches the sync that would, and `cache gc` reads every registered project's state and counts a candidate's files as needed. `status` lists the recipes with one under `candidates`, each with `compare::compare` of its files against the result data.lock pins and the cache file of each side of every file that differs, which `-v` prints for the rebuild, so a person can read them before `--accept`, and `stale` when `Candidate::answers`, the check `--accept` makes of a candidate's key, pin and tree, fails, as after a checkout of another commit, so its line says `--accept` refuses it rather than offering it. a build that pins another key or tree for the recipe drops its candidate, as `forget` does once data.lock is written. a candidate goes with its recipe too: where `Placing::apply` and `Placing::remove_only` write the state, after a relock or `remove` dropped the pin of a recipe data.toml no longer has, `State::forget_removed` drops its candidate, so gc frees its files.

`build --accept`, in `cli/build/accept.rs`, takes the project's hold and checks each candidate before it changes anything: its key must be the one `Step::read` gives against data.lock as it is, data.lock must still pin the key and the tree it was kept beside and its files must hash to its tree, as `Candidate::answers` checks, and the cache must hold every one. a refusal is `usage`, exit 2, and `output::fix` leaves its help alone, since `runs_code` counts every build. a candidate that passes is recorded with `record_result`, so the newest record of the key is the accepted tree, pinned with a new `locked` time, written with `Loop::write_rendered`, dropped from the state and placed by `sync_all` within the accepted recipes. nothing runs and nothing downloads.

## placing results

`plan` places a pinned result like a fetched dataset: its targets hold `Holder::Result` instead of a `LockedFile`, so `Placing::missing` never makes a download of one, while `Placing::wanted` asks the data folder and the mirrors for its objects as for any file. after them, `Loop::settle_unbuilt` takes the recipes whose results the placing needs bytes of that the cache lacks and no fetched file of the same run brings. a run of every dataset leaves them out with a warning: `Placing::leave_out` drops their targets that need bytes, so their files already in place stay and what an older pin placed at the others retires as an unwanted file, and the run records an incomplete sync and lists them in `Placement::unbuilt`. a run that names them, or `sync --locked` through `Loop::stopping_on_unbuilt`, refuses with `build.needed` before anything is placed. a dry run does the same when no mirror is set, counting an object the data folder holds as there. the build places its closure with `sync_all` once `data.lock` is written, `path` answers a pinned result's folder as for any dataset, `export` lists its files, and `cache gc` counts every pinned result's files as needed and keeps its record under `builds/`, while it frees any record no registered project pins once it is past gc's grace.

`status` finds the results sync would leave out in `unbuilt_here`: a result with a missing or outdated file whose bytes neither the cache, nor a file `compare` found in place with the same pin, nor a folder mirror at the `objects/` path `mirror::below` gives, nor a download of the same sync holds. their files leave `missing` and `outdated` for `unbuilt`, whose line names the fetched inputs the cache lacks too, and whose hint names the build. `holding` takes an input's file in place and an `adoptable` one alike, as `DataFolder` copies either into the cache, and `held` takes an archive the cache lacks as held when the cache or `holding` has each file its record lists that its members table keeps, as gc keeps them, so the line names only what the build must fetch. status makes no request, so a web mirror in the list leaves every result's files in `missing`, since sync asks it.

`Entry.place` false takes a dataset out of `plan::planned`, fetched or made: it has no target, so a sync downloads, unpacks and places nothing of it, and it clashes with no file, while what an earlier sync placed of it is unwanted and goes as `remove_unwanted` retires any file, an edit staying as `Reason::Unneeded`. `Placement.unplaced` counts, per dataset, the files that went, for the one `Retired <folder> · <count>, since <name> has place = false` line `tell` gives instead of counting them among the files no dataset needs. `path` refuses the dataset with `usage`; `status` lists it in `unplaced`, with a faint `Not placed` line that is no difference, and its leftover files as unneeded, which `Status.retiring` gathers by the dataset the state records them for, so its `Not placed` line says the next sync removes them instead of a line for each, and the sync hint says sync removes them; `list` gives `placed: false`.

a recipe changed since its build keeps its pin, and sync places it as it is. `tell_stale` runs in `sync_all` and `preview_all`, on the settled shortcut too, since edited code leaves data.toml and data.lock as they were, and in `path`'s ready answers: for each recipe in scope, `recipe::drift` against the run's lock, plus each fetched input whose data.toml entry moved past its pin, which a run of named datasets does not relock. a recipe with no pin warns `<name> is not built yet` in a run of every dataset; a run that names one stops in `refuse_unbuilt` with `build.needed`. code that cannot be read becomes a warning, never a failed sync.

the cache report and gc tell how a project uses each object it needs through `Readers`, [uses of needed objects](cache.md#uses-of-needed-objects): an input only builds read, a result's output, a pending input of a recipe still to build, or placed data. a recipe counts as built when data.lock pins it, `recipe::drift` finds nothing moved and the cache holds its whole result.
