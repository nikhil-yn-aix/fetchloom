# output

`Output` keeps human progress on stderr and machine-readable answers on stdout. command handlers provide facts and completion verbs; `Output` owns formatting, prompts and the final JSON envelope. `Work` counts operations independently of rendering, so tests can detect repeated work without timing the terminal. the [code map](codemap.md#output) lists its files; `src/work.rs`, `src/error.rs` and `src/units.rs` are under [primitives](codemap.md#primitives), and `src/cli/logs.rs` under [cli](codemap.md#cli).

## invariants and traps

- do not print directly from command handlers. renderer calls preserve stream routing and progress synchronization.
- never depend on color alone to convey an error or completion.
- bars draw only through `progress::terminal`, which puts the cursor back at the start of the last bar's line after each frame. indicatif pads every line to the last column, so the cursor would wait there to wrap, and the `^C` a terminal echoes at a stop would wrap onto a line of its own: clearing the bars then cleared that line and left the bar's last frame above `Stopping`. `a_stop_leaves_no_bar_behind` in tests/cli/progress.rs checks it in a terminal that echoes.
- snapshot filters remove paths, ports, times and rates. inspect unfiltered output when changing a value those filters can hide.
- literal error kinds are stable script interfaces. prose can improve without renaming them.
- masked display URLs do not sanitize raw URL values stored elsewhere. semantic argument errors, such as an unknown auth account, need the same masking as clap errors.
- an unhandled panic is fetchloom's own bug: `main` installs a hook that says so and where to report it, then hands over to rust's default report. normal errors use `Error` and `Kind`. a system that refuses the runtime's threads is found by a probe thread first and reported as `local.io`, while a refusal later, as tokio adds workers, still panics, and release builds abort; [worker budgets](primitives.md#worker-budgets) explains that exception.

## how it works

### lines and bars

each color has one meaning, named by a `Tone` in `src/output/style.rs`:

| tone | meaning | ansi theme | dark theme | light theme |
|---|---|---|---|---|
| `done` | finished work | green | `#a6cd6c` | `#367627` |
| `work` | work in progress and its bars | cyan | `#97cfa8` | `#296a42` |
| `warn` | attention or a difference | yellow | `#e3b257` | `#895900` |
| `fail` | failure | red | `#f17886` | `#b2263a` |
| `accent` | anything the user types, and choice numbers | cyan | `#97cfa8` | `#296a42` |

the dark and light colors live in one place, the two color schemes at the top of the documentation site's stylesheet, `docs-site/theme/assets/stylesheets/fetchloom.css`: `python/test_site.py` holds the two themes here to them, and `bench/render.py` draws the benchmark charts from them, so changing a color means changing it there and in `Theme::palette`. the site draws the transcripts its pages show with the same tones: `python/transcript.py` follows `verb_color`, `difference` and the setup, ticker, warning, error, hint and next lines here, so a verb or rule that changes here changes there too.

`Theme::detect` picks the theme: full-color terminals (`COLORTERM=truecolor` or `24bit`, `WT_SESSION`, or `TERM_PROGRAM` of vscode, iTerm.app, WezTerm or ghostty) get dark, or light when `COLORFGBG` ends in 7 or 15; every other terminal gets ansi, its own sixteen colors. `theme=` in `FETCHLOOM_COLORS` overrides the choice.

subjects are bold and supporting facts are dim. `FETCHLOOM_COLORS` replaces any tone's color for the run. it is read once, when `Output` starts; an entry it cannot read keeps the default and becomes one warning. color code asks for a tone through `toned`, `tinted` or `accent`, never a fixed color.

the welcome outside a project is `args::WELCOME` below fetchloom's name, version and `args::PURPOSE`: where to start, with a first command that needs the network and one that does not, the one command a clone needs, what fetchloom writes and where to read more. where stdout is a terminal wide enough for the name and the purpose under it, with room below for the whole welcome, fetchloom's mark hangs before the name: `PIN` in `src/output.rs`, the pin's head as a pin pushed into a sheet shows from above, a `•` in the bold accent, with the name and the purpose two columns in, where the welcome's commands start. one cell with nothing to join draws the same in every terminal font. where the terminal shows only ascii there is no mark, just the name with the purpose under it. elsewhere the name and purpose stand alone and wrap like the rest. `python/build_site.py` draws the same pin from the side for the site's pins and icons, and refuses a `PIN` whose head is not the `•` it draws.

help is clap's, laid out by `help::examples_first`: what the command does in a line, its usage, its examples, each with a comment where it needs one, its arguments named as the usage names them, a switch counted on repeat, as `-v`, by its name without clap's dots, its own `options`, then the `global options` every command takes under their own heading, what it changes on disk and its page. `fetchloom --help` and `fetchloom help` open with `args::ABOUT` and the examples a newcomer starts with, never the welcome, and end with the help topics. `-h` keeps the examples and the common part and says what `--help` adds: every option, where `-h` left some out, or else the global options and what the command changes on disk.

step and completion verbs are bold and right-aligned in 11 columns without status glyphs; a dry run's verb puts `Would` in the column and its action after it, as `      Would remove`. the subject before ` · ` is bold and its following facts are dim; a single-word subject is also bold. completed verbs include `Added`, `Fetched`, `Synced` and `Ok`. `Ok` says a state was reached, never one still to come, so `list <name>` shows a dataset data.lock does not pin yet through `mark`, as `Unlocked`, as `status` does. a verb whose words alone would give the wrong tone takes its tone where it is told, through `Output::step_in`, and `verb_color` stays as it is: a `Replaced` line that discards a person's own edit asks for attention. the labels of a report's facts, such as `cache`'s `Cache`, `Used by` and `Unneeded` or `settings`'s `Machine`, go through `Output::label`, bold in no tone, since a label is neither work nor its end. a search's rows show what to type in the accent, with no number, since `add` takes a reference; the picker numbers its rows, as keys that choose one.

warnings use yellow `warning:` with the help on a line below, and each has a kind, an `output::Warning`, which `--json` names in its `kind` beside `message`, `details` and `help`; a test holds the list in `src/output/warning.rs` to the one in the [JSON reference](../../user/reference/json-output.md#warning-kinds). errors use bold red `error:`, indented dim details and optional bold cyan `help:`. one error for several failed files or links, from `fetch::together` and `get`'s `some_failed`, tells failures alike once through `fetch::alike`: those of one kind with one help whose messages match once their own file or link and every address are taken out share the first one's line, the others listed under it, each named once, then their help. the first ten are named and the rest counted, while `failures` in `--json` keeps every one. a detail holds each SHA-256 whole, which `--json` keeps. `readable` shows a detail that compares two, as `expected sha256 <a>, got <b>`, or two MD5 values, as `stated md5 <a>, got <b>`, with every digit, one value under the other, since a person checks them against a published checksum. each label, without the `sha256` that 64 hex digits make plain, leads its value where both lines fit in 80 columns with the detail's indent, as `expected <a>` over `got      <b>`; a longer label, such as `the source states`, stands on a line of its own with its value indented under it, so no terminal wraps through a hash. it cuts any other word of 64 hex digits to 12, or to just past the first digit where it differs from another hash on the line, so hashes that differ late never read as equal; warnings use bold yellow `warning:`. a cancel the person chose and a stop they asked for are not errors: `Output::error` shows a cancel as a `Cancelled` line naming what was cancelled, and an `interrupted` error as a `Stopped` line made from its message, which starts with `stopped`, with its details dim under it. both use the warning tone and show their help as a hint; `--json` reports them as errors. hints are dim, with backticked commands in bold cyan. backticks remain when color is off. a hint, help or error that names a command for the project, or a `get`, builds it with `suggested::command`, which puts `-C` and the folder the run worked in before its words when the command line gave `-C`, so it runs as typed where the person typed it, and a git command for the project goes through `suggested::git`, which then gives git `-C` and the project's folder; commands for the whole machine and for other clones stay plain, and two tests in `suggested` find any other written out in the code. a word in such a command that came from data.toml, a link list or a server is a dataset name `name::is_dataset_name` accepts, or goes through `suggested::shell_word`, so a pasted command runs only what it shows; `suggested::command_words` reads one back as a shell would, for tests. welcome and help headings are bold, with commands and options cyan.

interactive progress shows filename, bytes, rate and estimated time left once the rate settles. bytes an earlier run kept count toward the bytes and the bar, never toward the rate or the time left: indicatif counts only what moves in this run, from 0 at each start, and the bar adds the kept bytes back when it draws. the rate and time left are the bar's own, over this transfer's last 10 to 20 s of bytes and time, from a second after it starts, so the bytes that arrive at once as a transfer begins, such as those a server sent while the run checked what an earlier one kept, read as no speed: indicatif's estimate gave such a resume `47.1 MiB/s` from a server sending 38.1. both run up to the last bytes that came, and the time left counts down from them, so a link sending its bytes in bursts never has its time left climb between them, as `17 s left` did to `20 s left` within 0.3 s. the time left rounds up to whole seconds, as a wait for the next try does, so a transfer under way never reads `0 s left`, and one too long to count in a duration reads as the longest. a lone download that finds such bytes says `Checking <file> · <size> kept from an earlier run` until its server answers. a file of a batch gets a bar of its own only once its download has lasted a second, as `Output::bar_after` makes it, so a batch of small files keeps the batch's line steady rather than drawing and clearing a bar for each many times a second. the bar for a batch fills to the sum of its files' sizes only once every size is known, from the source, a server's answer or a download that ended, so it shows no time left of its bytes while one is missing; once a file is done, it says about how long the rest takes at the pace of its files done, as `about 20 s left`. it says how many files are done, as in `Downloading 12 files · 3 done`, while others may still be under way. it counts downloads, not files: `Overall` counts files expecting one SHA-256 once, with the size any of them states as the batch begins, else the size the first of them to learn one tells, from its answer, its bytes, or, for one the cache served as its twin's download left it, that copy's size, and a file whose bytes the cache held not at all, as the command found them in the look it takes before its question, which the batch is handed rather than looking again, so a list whose files repeat bytes, or whose files sit in the cache, never says more downloads than it makes. a batch's own bar alone tells a time left, so a screen never shows a batch ending in 15 s above a file of it needing 29 s; from when a downloading bar knows its length until it can tell its own, it says the time fetchloom foresaw from the speeds it remembers of the hosts, as `about 20 s left`, which a bar that waits or checks never shows. the rate settles after 3 s, and the time left shows while its estimate reaches no further than 60 times the time watched, until 30 s have passed. a download that receives nothing for a second drops its time left, which no longer holds, and after 2 s shows `no data for 12 s` instead of a fading rate, or `waiting for the disk · 3 s` when its writer has every slot full, as `Event::Behind` says, since the disk then holds it rather than the network; a download's bar says `Connecting to <host> · 6 s` until its server answers, as one checking whether a cached file changed may wait, and names its file once the answer comes; `Moved::silence` counts the quiet only from that answer, while a batch's bar counts it from its start, so a batch with no bytes yet says `no data for 3 s`; one waiting to try again after a failed try shows which try comes next, of how many, and when, as in `try 3 of 5 · next in 2 s`, or `waiting for 127.0.0.1's rate limit · try 6 of 15 · next in 3 s`, until a try gets an answer; while one with every byte in shows `waiting for the disk` as the file is flushed into the cache, and how long since its last byte once that passes 2 s. once the first ctrl-c asks for a stop, `Alone::stopping` sets a flag every bar shares and redraws each bar at once, so each shows `stopping` after its counts from that moment, not from its next tick, and a stop that waits for a slow disk does not look like a network stall. a first ctrl-c that lets the run finish prints `Finishing` through `Alone::finishing` or `finishing_downloads` instead. every line goes out while `held` is locked, so `Output::alone`, holding it while a first ctrl-c is decided and told, keeps the lines of work that sees the stop until after that line; a question's held lines keep it with them until the answer. a line told at a ctrl-c clears its line first at a terminal, and every line there starts with a return to the start of its line, since the terminal echoes `^C` where its cursor waits, which shifted the verb column of the next line outside a bar. `Output::done` keeps the last closing line, and `Output::retell` tells it again at the end of a run that a finishing ctrl-c reached after it. a narrow terminal keeps the verb, so a person always sees what is happening, and the progress before the name: the filename shortens in the middle first, down to 24 columns, then the bar gives way to its percent, as `89%`, then the name shortens to 16 columns, the speed goes, the name shortens to 8, and the count goes last but the time left and the percent, so a hugging face shard at 40 columns still shows `Downloading`, how far it got and its time left, where it once showed neither a bar nor a time left, and at 80 columns once lost its verb as soon as its counters took their room. only a terminal too narrow for the verb and an 8-column name, under 20 columns, drops the verb, then the rest in the same order; a bar counts how far it got in the unit of its total all the way, with two decimals below one of it, as `0.98/2.0 GiB` rather than `1002.0 MiB/2.0 GiB` before `1.0/2.0 GiB`, and a narrow terminal shortens that fraction to the bytes done with that unit, `0.98 GiB`, before it drops it. a transfer's counters keep room from its first frame for the count at its widest, at its total or below one of its unit, as `0.94/6.0 MiB`, or `0.94 MiB` where a narrow line keeps the bytes alone, the speed as wide as `1023.9 KiB/s` and the time left as `59 s left`, and `Moved::hold` keeps the most room each took on the bar, so the line keeps one shape and the cut in its name stays put while the numbers change, a time left falling under a minute included; a stall's or a try's words take their own room only while they show. colored bars use `━` with a dim remainder where unicode shows; others use `#` and `-`, colored or not. waits show elapsed time without a spinner, and only they do: a transfer's bar shows no bare time beside its bytes, which read as time left. `MultiProgress` coordinates lines and bars so they do not overwrite each other. a question clears the bars and hides them behind a hidden draw target instead of suspending them, since a suspension holds `MultiProgress`'s lock until the answer and every other download's progress update would wait on it; lines told meanwhile are held and written after the answer, and one question waits for another. the time a download waits for an answer, asking or while another download asks, counts neither as no data nor toward its time or rate: `Bar::answered` starts its quiet clock again, takes the wait off its elapsed time and measures its rate from then on, and `Fetched::asked` holds the wait, which `Fetched::transfer` leaves out of the closing line, so a batch ends with the latest of its downloads once each leaves out its own wait. prompts read one key at a time with `read_key_raw`, so ctrl-c cancels them on every system and a hidden answer never leaves echo off. a yes or no question reads a line the same way: y, yes, n or no in any case, or enter alone for the default; any other line asks it again, so a q typed to quit never counts as the default.

non-terminal stderr has no bars, and lists such as search rows stay on stdout. a search whose stdout goes into a pipe or a file while a person watches stderr, as `Output::pipes_answer` says, as `| less` or `| grep` do, tells neither its table nor its `Found` line and hints there, which landed among the pipe's own lines. `Output::report` writes one row of a report, such as a file a status finds missing, to stdout in the same verb column and color `mark` uses, colored as stdout's own color decision says. where a person reads both streams at a terminal, a row wraps between words at stdout's width under its verb, as a story line does, so a long path's last letters never land alone at the first column; a pipe or a file gets each row on one line. `difference` gives each kind of difference one color wherever it shows, in status or push: the failure color for `Damaged` and `Blocked`, where the bytes in place are wrong or an entry stands in a file's way, and the warning color for every other kind, never the green of a finished step, so a pipe or a file gets the rows while `mark`, `done` and `hint` keep the story on stderr. JSON prints no rows, since its document holds them. `-q` keeps the rows and drops the story: they are the answer `-q` promises, as `list -q` and `cache -q` keep theirs, and a quiet status that printed nothing and exited 0 read as a project that matches data.lock. `Output::report_all` writes a list's rows the same way, gathered into writes of 64 KiB (`ROWS_AT_ONCE`), each ending with a whole row, rather than a write and a flush a row. `status` prints each difference it finds this way, a `-v` row under its row as a row with no verb: every file into a pipe or a file, and at a terminal, where `Output::answer_width` is known, at most 20 rows of each kind, a folder that holds no file now as one row. a command run below its project's folder prints a dim `using the project in ...` line for a person at a terminal. the steps before a command's own work, taking the project lock, opening the cache and reading the data folder, go through `Output::setup`, which logs a `-vv` debug line as each begins and, at a terminal, shows a live line such as `Locking the project · 3 s` once one lasts a second, since a slow disk or a network filesystem can make them take seconds with nothing else on the screen; a wait for another fetchloom replaces the locking line with its own. `Output::waiting` tells a wait whose words are too long for the terminal's line, as one on an owner record another system wrote, whole once, wrapped, and the live line under it counts the seconds alone, so the file it says to delete stays on the screen, and after a ctrl-c. work that is usually quick but grows with its size goes through `Output::lasting` the same way, with the plain lines a long batch tells where no bar shows: `Loop::apply` says `Placing 20,000 files` while `Placing::apply` checks and places them, and a sync that tells its steps says it as a step as soon as placing starts, once settling found the files it places: `Output::beginning` takes the batch's `Begun` flag, so the batch's plain lines never say it again, and its live line, which a step above now names, keeps the verb column blank and tells only its time, as `8 s so far`. an add, which tells what it placed in its own lines, `-q`, `--json`, a run that places nothing and one whose count changed while it settled say no such line, so the count is never contradicted. an import's walk of its folder goes through `Output::lasting_from_start`, whose live line `Reading <folder>` shows once the command, not the walk, has lasted a second, at once if it already has, since a folder of a million files takes seconds to read before the import can say anything else; its plain lines are a batch's. an import's `Copying` bar and its `Finishing` wait go through `Output::short_bar` and `Output::short_wait`, whose bars join the terminal's only once the command has lasted a second since `cli::run` started it (`Output::started_at`), whatever came before them, such as the folder's walk: a bar that comes and goes in less redraws every bar on the terminal, a flash a person cannot read. both steps share that one time, so `Finishing` never waits a second of its own, and a step that begins after it shows at once. until then a bar counts unseen, and `progress::Joining`'s thread adds each at its time, at most every 50 ms; an import that ends first draws no frame, its closing lines unchanged. where no bar shows, their plain lines are those of `Output::wait`. a batch says what it does after two seconds, then how far it got at ten-second intervals from the start, except one that waits on the network, as `progress::first` decides by its verb: a download says it as soon as it knows its size, from data.lock or from the answer's headers, with about how long it takes where the speeds this machine remembers give grounds, since `--json` hides the plan line that says so, and a lookup as it starts, so plain output tells at once that slow network work began, while quick work on this machine still adds no line. `--json` silences those lines unless `--progress` keeps them, for a script whose person still watches stderr, and `-q` silences them either way; `Output::ticker` makes that choice for every batch and wait. `fetch::planned_line` gives the line telling what a batch's downloads bring and about how long they take, as `Downloading 3 files · 1.2 GiB · about 3 min`, only where no bar shows: at a terminal the bars say it as they run, and a line saying the downloads were still to come once stayed above the closing one. a download batch with every byte in reports `Waiting for the disk to finish writing <what>` instead of its byte count, and its closing `Downloaded` line takes its rate from `Fetched::transfer`'s time until the last byte arrived, before the flush, and says the whole time when the flush took a second or more, naming that part: `1.0 GiB in 30.2 s, 12.3 s of it waiting for the disk · 57.2 MiB/s`. an unpack batch that has read every byte of its archives reports `Finishing <what>`, as its bar says, while their files are written and put in the cache. a download batch, and the line telling what it brings, as `Downloading 3 files · 1.2 GiB · about 3 min`, start at its first download, which `Event::Begun` marks once its claim holds and the cache still lacks the file, so a run that only waited for another fetchloom's download prints a `Waiting` line for that file and no download line, and a file whose bytes another file of the same batch brings says so, as `Waiting copy/iris.csv · the same bytes as iris.csv, downloaded once`, never that another fetchloom downloads them, and once that download's question about its size, if it asks one, is answered yes, so a no never follows a line saying the download began. a watched successful command can give a `next:` suggestion; ### terminal capabilities

stdout and stderr detect color separately. explicit `--color always` or `--color never` overrides environment settings. `auto` uses this order:

1. nonempty `NO_COLOR` disables color.
2. nonempty `CLICOLOR_FORCE` other than `0` enables it, even into a pipe or file, as the [CLICOLOR convention](https://bixense.com/clicolors/) asks.
3. a destination stream that is not a terminal gets no color.
4. `CLICOLOR=0`, `TERM=dumb`, `CI` or a coding agent's variable, below, set to anything but empty, `false` or `0`, disables it.
5. otherwise, color is enabled.

`--color always` and `CLICOLOR_FORCE` are the two ways to force ANSI into a pipe or file. labels retain their meaning without color. forcing color does not enable interactivity.

bars and questions need terminal stderr outside CI, outside `TERM=dumb` and outside a coding agent. `by_agent` in `src/output/style.rs` checks `AGENT_VARIABLES`, such as `AI_AGENT`, `VSCODE_AGENT` and `CLAUDECODE`; any value other than empty, `0` or `false`, read by `marks` as `CI` is, in any case, marks an agent, which also turns off automatic color. add a variable there only if agents set it and people's own terminals do not. questions also require terminal stdin. JSON, quiet mode and stderr debug logs suppress bars; quiet does not waive a question. a read of a terminal stdin that is no question, as `-i -` reads its links, says what it waits for through `Output::awaiting`, with the keys that end it, quiet or not, since a silent wait looks hung; JSON leaves stderr without it, as `Output::read_hidden` leaves its prompt. `FETCHLOOM_ACCESSIBLE` (`Style.accessible`), read as every on/off variable is through `settings::switched`, asks at such a terminal outside CI and agents, `TERM=dumb` included, and drops the bars there, since a screen reader reads each redraw again: progress comes as the plain lines a log gets, a choice is `picker::numbered`, its rows once and then a typed number, and an erased character is written over with backspaces where escape codes would show. `Output::asking` holds every line told during a question, with bars or without, the ticker's plain lines included, and writes them once it is answered. the dataset picker follows [selection rules](../../user/commands/search.md#choosing-a-dataset), including refusal to let `--yes` choose.

a question reads its keys one at a time with console's `read_key_raw`, which sets the terminal raw for one key and puts back the mode it found after it. `raw::question` in `src/output/raw.rs` holds the terminal in that raw mode, output processing kept, from before `Output::asking` or `Output::read_hidden` writes the prompt until the answer is read, so the terminal never echoes a key typed before the first read or between two, which would show a hidden key in the clear. ctrl-c stays a key for the whole question, so a second one cannot quit with echo off. a signal from another process, as `kill -INT` or `kill -TERM` sends, cuts the read short, which console reads as that key, and can end the question before the stop it brings is heard, so `Output::cut` notes any ctrl-c read and `Alone::stopping` then tells no `Stopping` line: the question's own `Cancelled` or `Stopped` line says what it cancelled. the mode it found comes back when the question ends, on an error or a panic too, and `Output::abandon` and the panic hook put it back for an exit that skips that, as a release build's abort on a panic does. windows reads key events, which its console never echoes, so it holds nothing.

`TERM=dumb` disables unicode choices. a windows terminal enables them only when `WT_SESSION`, `TERM_PROGRAM` or `ConEmuANSI` is present. outside a windows terminal, the first nonempty `LC_ALL`, `LC_CTYPE` or `LANG` enables unicode only when it contains `utf-8` or `utf8`, ignoring case. with none set, unicode stays enabled. `output::shown` gives each symbol fetchloom writes its ascii form: `-` for `·` and the bar's `━`, `...` for clipping, and `>` with worded key hints in the picker. the arrow between a value and the one that replaced it comes from `Output::arrow` as a line is made, `->` where only ascii shows, as `not set -> 5`, since an arrow a name holds, as `x→y.csv` does in the command a warning suggests, must stay as it is; an error's lines keep `→`, as its JSON document does. this is not an ASCII-only output mode: text from filenames and sources remains intact.

a line told on a terminal stderr, plain or interactive, wraps between words at its width, which the reader `story_columns` gives `Output::fitted` reads again as each line is told, so a terminal resized during a run gets lines as wide as it is now, and so does a yes or no question `Output::ask_yes_no` asks; a pipe, a file or a coding agent gets each line whole. `fit::fit` measures what a line shows, without its color or link escapes, and goes on under its own text: past a label such as `error:` or `help:`, past a step's 11-column verb, or at its indent. it never breaks between a number and its unit, and never inside backticks: a shell would run the first line of a command split there alone, as `fetchloom sync --force` without the file it names. a command is a unit with the punctuation after it, so no line starts with its comma: one that does not fit after the text moves whole to the next line under the text, or as far left as it needs to fit whole, never at the first column, and one wider than a line runs on there and the terminal wraps it, which most terminals copy as one line; that wrap is accepted, and a label such as `help:` may stand alone above such a command. a name in double quotes too wide for the room past the text wraps at its own spaces, and a word wider than it, as a long link or path, is cut where it stands, after its last `/` before the edge, so the names in it stay whole, each going on under the text, never from the first column, and never leaving a label alone on its line. that cut looks only in the word that crossed the edge, never back into a command before it, and punctuation right after a command goes with it. help at a terminal wraps its rows and examples too, in `wrap_help`. a row, such as an option and its description, wraps under its description column; when its name takes half the width or more, the name gets a line of its own and the description goes below it at column 10, deeper than a long option's name, so the two never run together. the comments of an examples block start at one column, past the widest command that has one, in a pipe too, unless one of them would then not fit; a block whose comment does not fit beside its command puts every comment on lines of its own below, and a command too long for a line goes on after `fit::MARK`, a backslash, or a backtick on windows for powershell, with an option and its value, or a redirect and its target, kept together. help into a pipe keeps each example whole.

a path with spaces in a story line can still break at one of its spaces, as `~/lab data/raw scans` would. `fit` sees only text, and nothing in a line says where a path ends, so it reads a path's spaces as it reads the prose around them. keeping a path whole needs a mark around each path a message shows, which `fit` would keep together as it keeps backticks, and which every place the text leaves fetchloom would take off again: the story, `message` and `help` in `--json`, and the logs. paths reach messages through `units::path`, 20 calls in 9 files, and through `.display()` in at least 57 more lines in 25 files, so the mark is a pass over all of them, and a sink that missed it would leak an invisible character into a path someone copies. until that pass, a path with spaces wraps as prose does; a copy of one that wrapped needs its line breaks taken out.

clickable URLs use OSC 8, a terminal escape sequence for links. they require interactive stderr and one of `WT_SESSION`, a known `TERM_PROGRAM` (`vscode`, `iTerm.app`, `WezTerm` or `ghostty`), numeric `VTE_VERSION >= 5000`, `KONSOLE_VERSION` or `TERM=xterm-kitty`. the presence of `TMUX` or `STY` disables them. link detection is independent of color; other terminals get the plain address.

### reports and counters

JSON is one completed document, not a stream of progress events; `--progress` adds no events to it, only the plain lines on stderr. it is indented when stdout is a terminal, which `Output` reads once into `indented`, and one line otherwise. at a terminal, `escaped_for_terminal` writes the c1 and bidi controls serde leaves raw as `\u` escapes, which only strings in JSON can hold, so a quoted line cannot steer the terminal; the human renderer's `plain` escapes the same characters, with every other control, in what it shows. it holds schema, command, status, result, warnings, errors and work. an error can carry a partial result and per-file failures. warning collection remains independent of whether human warnings are visible. encoding finishes in memory before stdout is written, so an unsupported path produces a complete error envelope instead of a successful truncated prefix. the one-line document is encoded into `Pieces`, buffers of at most 1 MiB, since one growing buffer copies itself at each doubling and the musl build's allocator keeps freed memory for a second, so the copies add to the peak. text answers retain write failures until command completion; help returns them directly. a broken pipe is successful, while other stdout failures make a successful command fail with `local.io`.

`Counts` snapshots atomic counters for requests, downloaded bytes, retries, resumes, object writes, downloads skipped, reflinks, hardlinks, copies, files placed from the cache, and the objects and bytes mirrors and the data folder gave. [JSON output](../../user/reference/json-output.md) defines the fields and counting contract. elapsed time is reported, but tests use deterministic counts rather than wall-time assertions.

`-v` prints work summaries; `-vv` enables debug events. `FETCHLOOM_TRACE` writes a Chrome trace through a guard that must live until command work ends. trace output is separate from the JSON contract. retry-command validation reads literal quoting rather than splitting quoted paths at spaces; it does not interpret shell expansions or operators.

flag help initializes the same palette as the `help` command. both apply `FETCHLOOM_COLORS` and warn about unreadable entries before printing help.
