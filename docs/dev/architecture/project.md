# project

`project` owns discovery, project records and the lock that serializes changes to one project's files. `Project` finds the nearest ancestor containing `data.toml`, without crossing the top of the git repository the search starts in, and reads the manifest, lock and local state. it also writes metadata and checks the data-folder chain; command handlers decide when those operations happen. the [code map](codemap.md#project) lists its files.

## invariants and traps

- commit the manifest and lock, not local observations. a copied state file is not proof of another machine's files.
- do not treat a broken lock like missing state. recovery may require restoring the lock from git or explicitly resolving all entries again.
- a tree hash pins archive contents without expanding the lock to one record per member.
- root discovery uses the nearest manifest. nested projects are distinct roots. a folder holding `.git`, a folder or a file, ends the search once its own manifest is checked, so a manifest above a repository needs `-C`; `ignored_in_git` uses the same repository test.
- path checks reject traversal and links in protected directory chains, but do not make a sandbox against another process swapping directories during a run.

## how it works

### three records with different authority

| record | establishes | failure behavior |
|---|---|---|
| `data.toml` | requested sources, filters, extraction and destinations, and the datasets `place = false` keeps out of the data folder | invalid input stops the command with a location and explanation |
| `data.lock` | resolved references, SHA-256, size and optional archive tree hash, or a recipe's inputs, command, code, key and result tree | malformed, duplicate-name or unsupported locks fail; silently resolving anew could pin different bytes |
| `.fetchloom/state` | what this machine placed and how it looked | unreadable or unsupported state counts as empty; matching files must then be checked before adoption |

`Manifest` uses `toml_edit` so add and remove can preserve human formatting. unknown keys fail. `place` is read on both kinds of dataset into `Entry.place`, true unless written false, and only ever takes placement away, since data.toml comes with whatever repository a person clones; it stays out of the spec and a recipe's key, so changing it pins nothing again. when either file fails to read and holds git's conflict lines at a line start, `Project` reports an unfinished merge naming the first such line instead of the parser's error, with `fetchloom lock` as its help and JSON `fix`. manifest citations omit a line's text when it overlaps a parsed reference span; invalid TOML has no trusted spans and cites positions only. this also protects inline tables and escaped keys without scanning every reference for every citation. the lock writer sorts datasets and files for stable diffs. `canonical::read` accepts the writer's narrow format quickly, then checks the same field grammar with comments; other valid TOML falls back to the general parser and the same path checks. escaped strings grow with the token being decoded; a long following URL does not reserve extra space for the path.

`Look` stores size and modification time, not the full filesystem metadata object. `Placed` also records the digest, dataset, method, writable mode, last checked time and whether the file was adopted rather than placed. an in-memory record can carry an intact racy hash from its current survey; neither the full nor the filtered state reader accepts that evidence from disk, and the writer leaves it out. `Synced` stores exact input hashes and completeness for the [settled shortcut](sync-loop.md#settled-sync-shortcut).

### mutation ownership

mutating commands acquire the OS file lock on `.fetchloom/lock`, then publish `.fetchloom/owner`. the owner record matters when windows and WSL share a project but cannot see each other's OS locks. `Held` removes its owner record before releasing the OS lock, including on an error path.

waiting commands poll every 200 ms, report the holder once and remain cancellable. a same-OS owner can be reclaimed after the OS lock is acquired; an owner from another OS needs conservative handling. an empty reservation never expires automatically: its writer may be paused on another OS, whose lock this process cannot observe. stale removal rereads the owner before deleting it. the record is flushed before it gets its name, so a power cut leaves a whole record, which the next same-OS command takes over, never an empty one. a command that holds the OS lock and cannot write the record, as on a full disk, goes on without it; without OS locks the record is the lock, so the failure stops the command.

a command that set out to start a project and added nothing removes `.fetchloom` with `Project::unstart`, taking out the lock file last while it still holds it. `hold` therefore checks, once it has the lock, that `.fetchloom/lock` still names the locked file (device and inode on unix, volume serial and file index on windows), and opens the name again when it does not, as partial claims do.

`status`, `list`, a ready `path` and `lock --check` need no mutation hold. a `sync` that cannot take the hold for a local I/O reason, as on a checkout this user may not write, answers without it when it would write nothing to the project: the settled check a dry run uses, plus an ignore rule already in place. it then takes the cache's shared hold to list the project, or only reads the cache when that hold fails too. anything else keeps the hold's error. a `path` that waits must reread the manifest and check readiness again because the preceding command may have completed the work.

### publication

metadata writes stage in `.fetchloom` when it exists, otherwise beside their destination. state is encoded into a complete JSON buffer before the staged file is written. they flush the new file and rename it into place. on unix, they then flush the destination directory and, when different, the staging directory. first creation of `.fetchloom` also flushes the project root. a directory-flush error after rename reports that the new file is already visible but its publication could not be confirmed durable. the manifest and lock remain separate replacements, not one transaction. the owner record has separate claim-and-publication rules because two OS environments must not both acquire it.

before a new add changes metadata, it saves exact recovery copies with exclusive names. the copies must be flushed before the first metadata replacement. a failed restoration retains them and reports their paths; their contents never enter diagnostics. a guard removes them on success or complete rollback.

payload durability belongs to [placement](placing.md#copy-durability). writing state only after copied bytes are flushed is part of the sync contract, not something `write_state` can enforce by itself.

## lock reading

runs read a lock with `Lock::read`, which loads and checks the lists a lock names below the project; `Lock::parse` is for tests. a command that names datasets may read them alone with `Lock::read_only`, which leaves the others out and reads no list of theirs; the narrow reader passes over the lines of their files unread, unless a quote or three double quotes among them could start a string that hides a line of the lock. data.lock has one format, `version = 1`; any other version is refused, a higher one with a request for a newer fetchloom. both readers give the same parsed datasets, each holding its files or the list that holds them, and one step then reads and checks the lists. before it reads any, it counts the files of the datasets it kept, inline or by their list's `file_count`, and refuses with `local.io` when reading them would take more than the room a container's memory limit leaves (`set_room`, from `Machine::container_room`): 650 bytes a file plus 8 MiB, 20 MiB on musl, a little under what a settled status took at 100,000 and 1,000,001 files, so a run that fits is not refused. a named read counts only the datasets it names. a writer writes missing list parts before `data.lock`, and `Project::sweep_lists` removes parts no lock names once the new lock is final: right after a command writes it, as `lock`, `sync`, `remove`, `drop`, `build` and a merge do, and after `add` commits, since a failed add puts the old lock back. `lists::folder` refuses a data.lock.d that is a link or a file, since a cloned project could point one anywhere: `Project::hold` asks it before a command changes anything, `lists::read` before a part is opened and `Project::write_lists` before one is written, and `Project::sweep_lists` leaves such a folder alone. `Lock` keeps fetched datasets in `datasets` and the results of recipes in `derived`, one name in one list only. a result's files always come from a list whose header is the tree's, `path\tsize\tsha256`, and reading recomputes its tree hash; a source list's header names its six columns, so one kind of list never reads as the other. only `fetchloom build` makes results: relocking moves them into the new lock unchanged, unless a fetched dataset now has the name, and the plan places their files as it places a fetched dataset's. already canonical locks use the narrow reader first. the next pass skips blank lines and valid TOML comments around the writer’s fields and after values. hash signs inside escaped or plain strings stay data. field order, duplicate checks, sizes and safe paths retain the same validation; other hand-edited TOML falls back to the general parser.

## state reading

`.fetchloom/state` is one compact json document: `version`, `at`, the `files` records in path order, `synced`, `candidates` and `blocks`. the writer cuts the records into blocks once one holds 64 KiB, and lists each block's first path and byte range in `blocks`, last in the document. `at` is the byte offset just past the records, written in a 20-byte slot right after `version` and padded with spaces, so the header is always the first 48 bytes and the writer fills the slot once the records are written, in the one buffer it publishes. a record's bytes are those serde writes for it.

a whole read, `Project::state`, takes a state of one block, at most 64 KiB, in one read of the length its open file reports. a larger one goes through the index too, a block at a time into one reused buffer: each block's records, checked as a read within folders checks a run, go onto one list in path order, and the map is built from the list at once, so a 100,000-record state's 24.7 MB are never held whole. a state whose index does not fit is parsed whole, `at` and `blocks` ignored. a survey of the whole data folder opens the state first and, when it holds 16 MiB or more, some 65,000 files, reads it on a thread of its own while it walks the folder, unless the run keeps to one worker; that took a settled sync of 100,000 files 0.79 of its time. a smaller state is read before the walk, since the thread's own heap took 11 to 18 MiB more memory for states of 2.4 to 12.1 MB. `Project::state_within`, which a ready `path` and a settled `sync <name>` use through `Survey::read_within`, reads the header, everything from `at` on, and only the blocks whose paths can fall at or below the named folders, consecutive blocks in one read: a path at or below `folder` sorts between `folder` and `folder0`, `0` being the character after `/`. beside 100,000 records that is tens of kilobytes rather than 24.7 MB. it checks what it relies on: the header, that the blocks cover the records end to end with one comma between two, that each run it reads starts at the path its index names and holds paths in order up to the next block's first, and that the bytes after the run are that path or the end of the records. so a changed index never changes the records it keeps: when anything does not fit, it reads the whole file with the whole read's filter instead, and the debug log says why. the `read_state` span records the bytes read.

two limits follow from reading part of the file. damage in blocks a read passes over is found by the next whole read, not by it. a hand edit that keeps every byte offset but moves a record out of path order can hide that record from such a read, which then sees its file as unrecorded and takes the long way, a whole read and a sync, never trusting more than a whole read would.

## merges

`lock` in a project whose data.toml or data.lock holds git's conflict lines merges instead of resolving. `markers::split` gives each file's sides from its conflict lines, and the base when every conflict shows one, as git's `diff3` and `zdiff3` styles do: the lines outside the conflicts with each conflict's base between them. lines outside the conflicts are what git merged by itself, which can be one side's change, so a side read from the conflict lines can hold lines of the other side: a recipe rebuilt on one branch beside a dataset added after it on the other gave our side their new list's name beside our list's hash. `conflicts::sides` therefore asks git for each side whole: `git::stages` reads stages 2, 3 and 1 of the index, ours, theirs and the base, with an empty base when git holds only stages 2 and 3, as for a file both sides added. data.lock merges from those whole sides and their base alone. data.toml keeps the sides its conflict lines give, which hold what git merged by itself and edits a person made since, and its base is the one the conflict lines show when it reads (`merge::reads`), else stage 1, else `trimmed`, the base without the outside lines of each table a conflict cuts, since zdiff3 moves the lines both sides share at either end of a conflict out of it. a file without conflict lines is the same on both sides; for data.toml, `git::committed` reads each side whole from `HEAD` and from `MERGE_HEAD`, `REBASE_HEAD`, `CHERRY_PICK_HEAD` or the parent of `REVERT_HEAD`, the commits whose index stages 2 and 3 would hold. a reading without a table only makes a dataset look new to the base, so it can turn a merge into a choice, never take a side's change unasked. when the conflict lines showed a base and none read, the error names git alone, since a style that shows the base is in use already.

apart from the steps `fetchloom build` runs, git is the one program fetchloom runs, and only as a reader (`git.rs`): the first `git` on `PATH` in an absolute folder, refused when it lies inside the project, started from its own folder with `-c core.fsmonitor=false`, with no shell, a closed stdin, `GIT_ALLOW_PROTOCOL` empty so no transport may fetch, 256 MiB of output and 10 s at most. reading objects also takes `--no-lazy-fetch`; a git that refuses the option with exit 129, as 2.43 does, reads again without it, still with no transport, so a partial clone's missing object fails the read instead of reaching the network. any failure means no sides from git, and the merge reads the conflict lines.

`merge` decides each dataset from its text alone on each side and at the base (`decide`): one side's change wins, alike sides stay, and anything else needs a choice. before it stops for one, `pinned_on_each_side` tells `-v` what each side's data.lock pins of the dataset: a result's key, the count and bytes of its files, and at most 3 of the files only that side pins, from the parsed entries without reading a list's parts; it never ranks the sides. the same values written apart keep one side's text with a warning. the text outside the datasets must agree or have changed on one side only, which picks the side whose document the merge edits; tables from the other side are copied with the comments touching their headers, in name order. the merged text is read again and checked against the decisions before anything is written. data.lock is merged at the level of parsed entries, so a listed dataset is compared by its list's names, count and hash without reading a part; a pin is kept only when its spec answers the merged entry, a choice for data.toml brings that side's pin, and recipe results merge by name. `decide_removals` then looks at each dataset a side of data.lock pins that the merged data.toml lacks: it goes with its entry when the other side left its pin as the base had it, and needs a choice when that side changed or added its pin, since a re-import or `lock --upgrade` leaves the entry's text alone and git takes the removal in data.toml unseen. a choice takes its side whole when git gave the sides: `chosen_whole` writes that side's entry for the dataset, or takes it out, and the pin kept is that side's. without git, a choice that would need an entry no side of the conflict lines holds stops with help to copy it by hand. `kept` reads only the kept pins' parts, one pin at a time, through the usual reader; a pin that does not read stops the merge with help to copy that side's table and parts back by hand, so its JSON `fix` is null and nothing advises pinning anew.

## lists git has

a list's name in `data.lock.d` holds its dataset's name and its content's hash, so a rebuild writes a new file, which `git commit -a` leaves out, and a clone of that commit stops at `lists::read` with `project.invalid`, saying the list was probably not committed and how to get it. `Project::write_lists` returns the parts it wrote anew, which each writer notes on the run's `Context`; once a command succeeds, `finish` in `cli.rs` hands them to `remind_lists` in `cli/project.rs`, which asks `git::tracked` for the files git's index has below `data.lock.d` (`git ls-files`, which reads no object, so any git does) and names those git lacks: a `next:` line for a person at a terminal, else a warning. `status` names every part data.lock names that git lacks the same way. with no git, outside a repository, or for a part git has, nothing is said.

a recipe's key hashes its code, so a code file a commit leaves out leaves a clone unable to build it from the same code. `warn_recipe_code` in `cli/project.rs`, which `status` and a build that ends well call, lists the files each `code` entry of data.toml takes in with `recipe::code::files`, the walk `code::hash` makes without reading a file, and asks `git::known` once for all of them: `git --literal-pathspecs ls-files -t --cached --others --exclude-standard`, which reads the index and the ignore rules and no object, and tells the files git has from those it lacks; a file in neither is one `.gitignore` leaves out. a file below a submodule or a repository inside the work tree counts as git's. it warns of the files git lacks with their `git add`, and apart of those `.gitignore` leaves out with `git add -f`; `-v` names each. with no git or outside a repository it says nothing.

## ready path waiters

a waiting `path` notices a changed state file and runs the normal read-only readiness check before trying the mutation hold again. waiters whose files are now ready can finish together instead of handing the owner record from reader to reader. the state stamp only triggers a recheck: fresh state alone never vouches for missing, changed or doubtful files. unchanged stamps and failed readiness checks keep the normal hold-and-reread path.
