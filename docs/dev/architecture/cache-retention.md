# Cache retention

## retention and cleanup

successful sync registers the project root. gc follows registered manifests and locks, including needed archive members: those each project's members tables keep, read from its data.toml, or every member when that data.toml does not parse or two glob keys match the archive. an archive's own bytes, each part of a split one, stay needed only while this machine never unpacked it or lost a member it unpacked to. unreadable registrations or project inputs stop gc; only a missing manifest makes a project stale. inspection queues stale project roots, and the sweep removes their registrations alongside other cleanup. `needed_by_all`, which `get -o` asks before it lets bytes leave the cache, and `needed_for_drop`, the same question narrowed to the archives an unpack may drop, follow the same rule: a stale project needs nothing, so neither keeps what gc would free, while an unreadable one makes them keep everything. `needed_for_drop` checks the members of a candidate archive only, each once however many projects pin it, on the run's workers; an archive none of whose files is a candidate keeps its bytes whatever its members say. both read only the kept rebuilds of each project's state, which its index places after the records. a failed registration removal retains its original I/O cause in `not_removed` and prevents a successful gc result. a project's first sync registers it only after placing, and `get` never registers, so registration alone cannot protect what a running command is about to place: every command that opens the cache through `cli::open_cache` holds `gc.lock` in the cache root with a shared lock for as long as any clone of that `Cache` lives, and gc takes it exclusive through `Cache::hold`, polling so ctrl-c can end the wait. dry runs read the cache unopened and take no lock. unneeded objects and unpack records become eligible after 24 hours by modification time, or immediately with `cache gc --now`. the CLI passes zero object grace to `sweep_with_stop` only for `--now`, otherwise `GRACE`; `sweep` in cli/cache.rs counts the objects `Cache::imported` lists that the sweep freed apart, and for `--now` adds to the needed objects every listed one the question before the hold did not cover, then `Cache::forget_imported` drops each list naming no object left; unfinished downloads nobody holds keep the full day unless the grace is zero, and held partial locks protect running downloads either way. `Cache::unfinished` totals what `partial/` holds for `fetchloom cache`, by the blocks each file takes on unix rather than its length, since a split download leaves holes in its file until it finishes; windows makes no holes there, so its length counts. gc's leftover bytes count the same way. and `Cache::explained` adds that total to a disk-full error from a cache write, as it adds the refusing folder to a permission error. removing their cache names does not remove placed hardlinks, reflinks or copies.

exclusive cache access fails on every lock error, so gc never treats failed exclusion as permission to delete. gc also refuses when a read-only root prevents opening the lock: an object subdirectory can be a different writable mount. shared access may continue only when locking is explicitly unsupported; other errors stop it. opening another user's lock file read-only still permits a shared lock. on NFS that descriptor cannot take an exclusive lock, so gc refuses and reports the locking error instead of proceeding.

archive staging holds an OS lock until publication or discard. the next unpack or gc immediately reclaims unheld staging; held locks protect active work regardless of age. without locking, staging needs 24 hours without a write before reclamation. a recipe's step runs in a `.build` folder under `tmp/` with the same lock; what a step left there, such as read-only files and folders it took its owner's access from, goes with `clear_tree`, which never follows a link. `builds/` is created when a build first records a result; gc keeps every object a registered project's pinned results name, and their records, which `Needed.results` holds by key and tree. `sweep_results` removes any other record once `unused` finds it old enough, as one a build left when it failed before writing data.lock, then the key's `lock` and folder once no record is left; a build holds the cache shared for its whole run, so the exclusive sweep never takes a lock one waits on.

`Usage::measure` tells where the space goes, from one object scan and the needs walk gc uses: what registered projects need and how much of it has another name, unneeded bytes gc frees now, those that wait for their day, and those a name outside the cache keeps, which gc removes without freeing. all are payload bytes, as gc counts them. on unix the scan's own metadata gives each object's link count, so this costs no extra call; a windows listing does not count links, so there `place::has_other_names` opens each object once. copies come from each registered project's `.fetchloom/state`: a placed file whose object the scan found gets one `symlink_metadata` call, and counts while its size and modification time match the state's record, as a copy or clone, or as a hardlink with no other name. windows opens such a hardlink once more to count its names. the calls run on `place::run_all`, since each waits on the disk; for 100,000 files that took the pass from 0.40 s to 0.18 s, [measured](../performance/measurements.md#the-cache-report-on-100000-placed-files-2026-11-11). `fetchloom cache` renders it and the weekly reminder in cli/cache.rs uses its `freeable`, so the two cannot disagree. `inputs_only` sums the needed objects whose every use is an input, as below, and stays none when the needs walk told no uses.

## uses of needed objects

gc keeps every object a registered project needs, whatever the project does with it; `Needed.uses` adds how each project uses each one, so `fetchloom cache` can say how much only builds read, and `cache gc --inputs` frees only the raw input of that, where a folder mirror holds a copy, as [below](#freeing-raw-input). `needed_with` tells uses only when its caller asks, `Uses::Told`, as `cache` does, or `Uses::Grouped`, as `cache gc --inputs` does, since it reads every registered project's recipes and their code; gc, `get` and the unpack that drops archives ask only what is needed. `Readers` holds, for one project, the recipes that read each dataset and whether each is built: data.lock pins a result of it, `recipe::drift` finds nothing moved, which reads its code, and the cache holds every file of the result; code that cannot be read counts as moved, which keeps more.

| `Use` | the object is a file of |
|---|---|
| `Input(Source)`, `Input(Imported)` | a fetched dataset with `place = false` that recipes read, each of them built; an import's bytes come back only from a mirror |
| `Input(Derived)` | a recipe's result with `place = false` that recipes read, each of them built, which a build makes again |
| `Pending` | a fetched dataset a recipe still to build reads |
| `Output` | any other recipe's result, or a rebuild a project's state keeps for `build --accept` |
| `Placed` | any other fetched dataset, one with `place = false` that no recipe reads included |

an object two projects, or two datasets, use takes the use `Use::and` gives: an input only while every use is one, then from the supply that brings it back most readily. a project whose data.toml does not read tells no use but placed or output, so it keeps all its objects out of `inputs_only`.

## freeing raw input

`src/cli/cache/inputs.rs` runs [`cache gc --inputs`](../../user/commands/cache.md#raw-input-a-mirror-holds). with `Uses::Grouped`, the needs walk also lists each dataset with `place = false` that recipes read as a `Group`: its project, its use from `Readers`, the recipes that read it, those not built, and the objects `add_with_stop` adds for it, so the objects `cache gc --inputs` looks at are exactly those gc keeps for it, members tables and split archives included. a group whose use is `Input(Source)` or `Input(Imported)` is raw input. `plan` keeps an object of raw input whose merged use is anything but an input, or that a recipe's result with `place = false` shares, or that `Object::has_other_names` finds linked; it reads the copy of each other one on each folder mirror in turn, through `mirror::folder::check_all`, which opens a copy without following a link, as `copy_in` does, asks for it past memory where the system allows, as push's read-back does, and hashes it whole, at most eight at a time on one mirror. the first copy that hashes to its name is the object's route; a damaged or unreadable one is kept as the reason when no later mirror has a good copy. a mirror without its marker is warned about and skipped, and web mirrors are never read.

`Input(Derived)` stays: every build puts back a pinned result the cache lacks, from a mirror or by running its recipe, so freeing it would last only until the next `fetchloom build`, and while it is gone the inputs its recipe reads turn pending.

the plan is made before anything is held or asked, as a dry run reads the cache, so reading hundreds of gigabytes and waiting for a person's answer never hold the exclusive lock other runs wait on. after a yes, it takes that lock through `hold`, as plain gc does, walks the needs again, and `recheck` keeps an object that is no longer raw input nothing else keeps; then `free` looks at each copy once more, `folder::still` comparing its size and modification time with those it had when it hashed, and removes the object with `Cache::free_input`, which refuses a removal through a folder swapped for a link as every sweep does. the copy's number is left out of that look, since a network disk may give a file a new one, as push finds. plain gc's sweep runs last, under the same lock. a dry run frees through a pretending cache, so its `changes.remove` lists each object.

`cache verify` rehashes all objects and marks damage without deleting it. on linux, when the objects are out of memory, it reads ahead of its workers as [verification workers](placing.md#verification-workers) describes. its bar moves as each 1 MiB block is read, so one large object never holds it still. if the OS refuses a verification worker, the caller completes that work instead. those marks also tell project scans to check already placed hardlinks.

inspection, verification reads and cleanup retain each failed path with its I/O kind, OS error code when available, and original message. JSON `not_removed` and `unreadable` contain these failure records, not bare paths. warnings and error details retain the same causes; storage failures do not receive permission-only advice.
