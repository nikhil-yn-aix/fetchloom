# Cache retention

## retention and cleanup

successful sync registers the project root. gc follows registered manifests and locks, including needed archive members: those each project's members tables keep, read from its data.toml, or every member when that data.toml does not parse or two glob keys match the archive. an archive's own bytes, each part of a split one, stay needed only while this machine never unpacked it or lost a member it unpacked to. a dataset `add --no-sync` pinned needs each file its source states by SHA-256, or by MD5 when the cache recorded which object that link's bytes hashed to, so what a first sync downloaded before it was cut short stays for the sync that finishes it. a lock with an import waiting for its list, as on a branch where data.lock.d is untracked, needs every object `Cache::imported` lists, since which are its own is unknown and no source gives one back. `scan_objects` refuses a fan folder that is a link or a file before it lists it, as `place::NotCacheFolder`, whose `Failure` advice says to remove the link itself, so neither gc nor verify counts, removes or hashes what a planted link leads to. unreadable registrations or project inputs stop gc; only a missing manifest makes a project stale, unless `Cache::out_of_reach` finds its disk gone: a registration records the device number of the project's disk where that number is its own, a unix device with a major number, or a windows volume's serial, and a project whose nearest folder that is there sits on another disk, or on no drive at all, is out of reach, which stops gc as an unreadable project does. `manifest_of` in cli/cache.rs reads each registered data.toml with `Project::read_own`, as a plain file of at most 256 MiB, never through a link and without waiting on a fifo, since a commit pulled into a clone, or anyone sharing the cache in their own project, can make it a fifo, a link to /dev/zero or a link to a file outside the project, which every walk of the projects would wait on, read without end or read in its place, unpacks in other projects included. inspection queues stale project roots, and the sweep removes their registrations alongside other cleanup. `needed_by_all`, which `get -o` asks before it lets bytes leave the cache, and `needed_for_drop`, the same question narrowed to the archives an unpack may drop, follow the same rule: a stale project needs nothing, so neither keeps what gc would free, while an unreadable one makes them keep everything. `needed_for_drop` checks the members of a candidate archive only, each once however many projects pin it, on the run's workers; an archive none of whose files is a candidate keeps its bytes whatever its members say. `drop_archives` asks it only about the archives whose bytes the cache still holds, so a sync after which every archive is already dropped reads no registered project: a run that adds one link to 100,000 datasets of a zip each otherwise looked at all 300,000 members. both read only the kept rebuilds of each project's state, which its index places after the records. a failed registration removal retains its original I/O cause in `not_removed` and prevents a successful gc result. a project's first sync registers it only after placing, and `get` never registers, so registration alone cannot protect what a running command is about to place: every command that opens the cache through `cli::open_cache` holds `gc.lock` in the cache root with a shared lock for as long as any clone of that `Cache` lives, and gc takes it exclusive through `Cache::hold`, polling so ctrl-c can end the wait. dry runs read the cache unopened and take no lock. unneeded objects and unpack records become eligible after 24 hours by modification time, or immediately with `cache gc --now`. the CLI passes zero object grace to `sweep_with_stop` only for `--now`, otherwise `GRACE`; `sweep` in cli/cache.rs counts the objects `Cache::imported` lists that the sweep freed apart, and for `--now` adds to the needed objects every listed one the question before the hold did not cover, then `Cache::forget_imported` drops each list naming no object left; unfinished downloads nobody holds keep the full day unless the grace is zero, aged as objects are by the later of the modification time and the ctime, since a seal dates a finished part back to its first byte and a run may die before publishing it, and held partial locks protect running downloads either way. `Cache::unfinished` totals what `partial/` holds for `fetchloom cache`, by the blocks each file takes on unix rather than its length, since a split download leaves holes in its file until it finishes; windows makes no holes there, so its length counts. gc's leftover bytes count the same way. and `Cache::explained` adds what of that total `cache gc --now` frees, the downloads whose lock `unfinished_unheld` takes as the sweep does, opened without following a link or waiting on a fifo, to a disk-full error from a cache write, as it adds the refusing folder to a permission error. removing their cache names does not remove placed hardlinks, reflinks or copies.

exclusive cache access fails on every lock error, so gc never treats failed exclusion as permission to delete. gc also refuses when a read-only root prevents opening the lock: an object subdirectory can be a different writable mount. shared access may continue only when locking is explicitly unsupported; other errors stop it. opening another user's lock file read-only still permits a shared lock. on NFS that descriptor cannot take an exclusive lock, so gc refuses and reports the locking error instead of proceeding.

archive staging holds an OS lock until publication or discard. the next unpack or gc immediately reclaims unheld staging; held locks protect active work regardless of age. without locking, staging needs 24 hours without a write before reclamation. a sweep opens each lock file to read and write where this user may: nfs and smb lock byte ranges for flock and take no exclusive lock through a handle open only to read, which a sweep would take for a disk without locks and so clear staging still in use once it is old.

a removal in the cache, through `remove_inside`, goes through one `Placer` the cache keeps for every clone, which holds each folder on the file's way while it removes the file. gc's sweep frees the objects its scan found a fan folder at a time, in the scan's order, which lists each fan's objects together, so each fan is a run of the scan freed where it lies. once anything is to be freed, the fans go to up to eight workers, one for each 32 fans, within `FETCHLOOM_THREADS`; a dry run keeps one thread, so the removals it lists keep the scan's order. on unix it removes them through one handle on each fan folder, opened below the cache's root at the fan's first removal without following a link, so a fan swapped for a link meanwhile sends no removal elsewhere; a fan that will not open goes the way of `remove_inside`, which says why each removal is refused. a dry run removes nothing and opens no fan.

`Usage::measure` tells where the space goes, from one object scan and the needs walk gc uses: what registered projects need and how much of it has another name, unneeded bytes gc frees now, those that wait for their day, and those a name outside the cache keeps, which gc removes without freeing. all are payload bytes, as gc counts them. on unix the scan's own metadata gives each object's link count, so this costs no extra call; a windows listing does not count links, so there `place::has_other_names` opens each object once. copies come from each registered project's `.fetchloom/state`: a placed file whose object the scan found gets one `symlink_metadata` call, and counts while its size and modification time match the state's record, as a copy or clone, or as a hardlink with no other name. windows opens such a hardlink once more to count its names. the calls run on `place::run_all`, since each waits on the disk; for 100,000 files that took the pass from 0.40 s to 0.18 s, [measured](../performance/measurements/placement.md#the-cache-report-on-100000-placed-files-2026-11-11). `fetchloom cache` renders it and the weekly reminder in cli/cache.rs uses its `freeable`, so the two cannot disagree.

`cache verify` rehashes all objects and marks damage without deleting it. on linux, when the objects are out of memory, it reads ahead of its workers as [verification workers](placing.md#verification-workers) describes. its bar moves as each 1 MiB block is read, so one large object never holds it still. a large object hashed alone, and each of a batch's two largest from its first block, is read on a second thread a block ahead of its hash, as [verification workers](placing.md#verification-workers) describes. if the OS refuses a verification worker, the caller completes that work instead. those marks also tell project scans to check already placed hardlinks.

inspection, verification reads and cleanup retain each failed path with its I/O kind, OS error code when available, and original message. JSON `not_removed` and `unreadable` contain these failure records, not bare paths. warnings and error details retain the same causes; storage failures do not receive permission-only advice.
