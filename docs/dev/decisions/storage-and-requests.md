# Storage and requests

| what | why | invariant |
|---|---|---|
| try reflink, hardlink, then copy; read-only windows placement tries hardlinks first | reflinks isolate later writes; hardlinks share bytes and can reuse a windows scan; copies work when links fail. symlinks can dangle after cache cleanup and need extra windows privileges | [placing](../architecture/placing.md#choose-a-filesystem-method) |
| publish a cache object by a link or a rename that refuses a taken name, and by a plain rename only on a disk with neither | a check before a rename that replaces let another writer's object, published between the two, lose its name; FAT and exFAT have no links, but linux, macos and windows can rename on them without replacing. a disk with no such rename still works: the object's name is its verified SHA-256, so a replacing rename swaps identical bytes, and refusing the disk would gain no safety. a person's files never get a replacing rename | [cache publication](../architecture/cache.md#publication-and-repair) |
| separate object publication from partial ownership | hardlink publication avoids serializing publishers on one exclusive cache lock; unfinished bytes need an ownership lock, and the shared gc lock protects active runs | [cache publication](../architecture/cache.md#publication-and-repair) |
| flush and name a group of finished downloads once its first waited a second, with the one `syncfs` a full group takes | a run that waited on nobody kept its last group claimed until its longest download ended, so a second run on the same cache waited for that download: 26.4 s against 12.9 s. flushing each file of a waiting group was not reliably faster on nvme, and slower on a shared disk holding another program's unwritten data and with 10,000 files | [measurements](../performance/measurements/placement.md#a-second-run-on-a-shared-cache-2026-11-12) |
| open cache hashing and copy inputs without following final links | a replaced object name must not redirect these readers to another file | [cache access](../architecture/cache.md#safe-object-access) |
| date each object by its birth when sealing it | an edit through a placed hardlink changes the cache's copy behind fetchloom's back; a modification time moved past the birth time puts the object in doubt with one stat and no per-object record, as pnpm's recorded check time does for its store. the date lands just past the file's making, which an nfs 4.2 server with delegated timestamps keeps | [cache access](../architecture/cache.md#safe-object-access) |
| keep a link's changed copy beside the pinned file sync puts back | an edit made in place through a writable hardlink changes the cache's copy every project shares, so sync must put the pinned bytes back; scripts such as pandas' `to_csv` write in place, so dropping the changed copy lost real work. a second name for the same file costs no bytes, and a name already taken is refused, never replaced. a copy other projects' links still share is cloned or copied instead, since one shared `.changed` file let an edit in one project change another's; on a disk without clones that costs one copy a project, in this repair only | [local changes](../../user/commands/sync.md#local-changes) |
| flush a run of up to 64 files one by one, and a larger one with one `syncfs` | `syncfs` also waits for everything other programs wrote to the filesystem, which took seconds on a busy disk; one by one cost an idle disk under 10 ms more for 64 files, and one large file the same either way | [batch durability](../architecture/downloads.md#batch-durability) |
| flush copied payloads before sync writes state | state must not vouch for bytes still pending write-back; linux batching avoids one flush per small copy | [copy durability](../architecture/placing.md#copy-durability) |
| leave checkpoint and lookup indexes as unflushed hints | losing a hint costs resumption or revalidation, while payload identity remains checked | [cache checkpoints](../architecture/cache.md#partial-ownership-and-checkpoints) |
| show 12 search matches when `--limit` is not given, every catalog's best among them | seven catalogs' three matches each made 21 rows, more than a picker can show on a terminal 24 rows high. each catalog's best first keeps every catalog in view, names typed exactly come next, and `--limit` still shows all it asks for | [search](../../user/commands/search.md#results) |
| search ENA and dandi only when `--source` names them | in searches of new words ENA answered 3 of 24 and dandi took 2 to 4.5 s, so the 3 s grace left them out with a warning; a search without `--source` should be quick and quiet, and a genomics or neuroscience search is one flag away | [search](../../user/commands/search.md) |
| give the other sites 3 s once one has answered a search of every site, and 10 s when `--source` names them | one failing catalog held the dataset picker for 76 s while the others had answered, and ENA, slow on words it has not seen, held 13 of 16 searches for new words the whole 10 s; a named site gets the longer wait, and a slow network still gets unlimited time for the first answer | [search](../../user/commands/search.md) |
| save any website's token, header or cookies under its host with `auth login`, in the key store, and send them to that host and port alone, on a request's first origin, over https or plain http only to this machine or an `allowed_origins` origin, and never through a proxy | a person signs in to a site once and every link to it works, as curl's `-H` and `-b` or yt-dlp's cookies do, without a key in data.toml, which a cloned project could point at any host. a key bound to its host and port never reaches another port, curl's CVE-2022-27776, and one that stops at the first redirect off its origin never reaches a host the link sends fetchloom on to. plain http shows a key to every network on the way; loopback never leaves the machine, and an origin `allowed_origins` lists is a network the person vouched for, but a proxy on the way reads a plain http request whole, and `HTTP_PROXY` carries even a loopback link unless `NO_PROXY` names it, so the rule covers `.netrc` logins too | [where a key goes](../../user/concepts/privacy.md#where-a-key-goes) |
| keep the cookies a host with a saved credential sets in a jar of that site's own, never the run's shared jar | the shared jar goes with any request that has no cookie header of its own, by plain cookie rules, so a session the site renews without `Secure`, or with a `Domain` covering other hosts, would reach plain http, a proxy or a sibling a cloned data.toml names. the site's own jar goes only with its credential, by the same host, port, first-origin and plain http rules, so a renewed session still reaches the site | `Sites::cookies` and `Net::site_headers` in [src/net/site.rs](../../../src/net/site.rs), `Cookies` in [src/net/cookies.rs](../../../src/net/cookies.rs) |
| read browsers' cookie databases with a reader of SQLite's file format in the crate, and keep SQLite itself, through rusqlite, for the tests | a site's cookies are one table's rows, which SQLite's documented file format and write-ahead log give in a few hundred lines, and reading the files takes no lock a running browser holds. the crates that read browsers' cookies fail deny.toml: rookie 0.5.6, of 2024 and in minimal maintenance, brings libesedb's LGPL-3.0-or-later and CC0-1.0 code, 201 crates and 3.8 MB to a release build of its own, and unsafe code that impersonates SYSTEM for chrome's app-bound keys; cookie-scoop 0.1.1 brings MPL-2.0 through dirs and runs `security` and `secret-tool`; decrypt-cookies is LGPL-3.0-or-later. rusqlite with SQLite bundled passes, but added 1.9 MB and a C build, so SQLite writes the tests' databases instead and the reader is checked against it, on firefox's and chrome's tables at browser size: thousands of rows on pages of 4096 and 32768 bytes, interior and overflow pages, a free list, an index, a log restarted after a checkpoint, and rows older than the columns a migration added, which read as SQLite reads their defaults. a crafted file costs the reader no more than its budget: it refuses a page reached twice and cells that share bytes, and charges each row for the values it builds before building them | [any website](../../user/guides/sign-in.md#any-website) |
| read chromium's cookies on linux and macos with the key from the system's own store, in the process, and not on windows | chromium seals cookies with AES-128-CBC under a key its own code derives with PBKDF2 from a secret in the secret service or the keychain, so `keyring`, already the key store, finds it, and `ring` and the `aes` and `cbc` crates, two of them already under keyring on linux, open them; no program runs, and macos asks the person before giving the key, as it asks for any program. on windows chrome seals cookies with app-bound encryption since version 127, which only its own program may open (chromium's chrome/browser/os_crypt), and the older DPAPI keys need a windows call through unsafe code or another crate, so firefox and cookies files serve windows | [auth](../../user/commands/auth.md#any-website) |
| let data.toml ask for a web page with `web_page = true` | a page at a link whose name has no extension is refused, since it is most often a folder listing or a sign-in page, but some data is only a page. the setting changes only whether a page counts as the file; it adds no host, header or key, so a cloned repo can carry it as it carries `extract`. it holds on every path: the cache's record of a link remembers a page, so bytes the cache answers with, offline, after a 304 or after waiting for another fetchloom, are told as a page again, a listing's `ETag` never vouches for a kept page, and the line joins data.lock's spec, so taking it away asks the link again rather than keeping the page's pin, while the entry's own `web_page = true` keeps a relock from carrying that pin when a select or exclude changed with it, where a check of the spec alone would match neither way | `Fetch::page` and `recalled` in [src/net/download.rs](../../../src/net/download.rs), checked in [src/cli/fetch.rs](../../../src/cli/fetch.rs); `spec`, `Locked::web_page` and `page_no_longer_asked` in [src/project/lock.rs](../../../src/project/lock.rs) |
| offer a website's sign-in through the refusal path, with a picker of the ways in at a terminal | a 401 or 403 seldom says what a site takes: a basic challenge asks for a username and password and a bearer one for a token, while most sites name nothing, since people sign in on a page. so the help names `auth login <host>` with each option, and a terminal asks which. the host keeps its port, since a key saved for port 443 never goes to another | `Net::refused` in [src/net/site.rs](../../../src/net/site.rs), `site::offered` in [src/cli/auth/site.rs](../../../src/cli/auth/site.rs) |
