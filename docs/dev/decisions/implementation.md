# Implementation

| what | why | implementation |
|---|---|---|
| keep one rust crate | modules provide boundaries without separate package versions; split only when an independent consumer needs one | [architecture](../architecture/README.md) |
| ship one executable, `fetchloom`, and give it the short name `fl` by a link beside it, never in place of another `fl` | a link follows every upgrade and needs nothing more downloaded, so it cannot fall behind, and messages, docs and scripts keep the one name `fetchloom`. the windows installer makes its hardlink again on each install, since a hardlink keeps the old bytes, and the wheel, which can hold no link, runs a python launcher. powershell runs its `fl` alias for `Format-List` before any program, so there `fl.exe` or the user's own alias gives the short name | [installers](../engineering/releasing.md#installers) |
| keep adapters in the crate | version, checksum and paging rules stay beside their tests; there is no current plugin-protocol consumer | [sources](../architecture/sources.md) |
| route DOIs through the registered handle URL | DOI prefixes and landing-page redirects do not reliably identify the repository | [source routing](../architecture/sources.md#parse-before-resolving) |
| support shared-link sources alongside repositories | research inputs also arrive through hugging face, kaggle, drive and dropbox | [source behavior](../../user/sources/README.md) |
| use reqwest, tokio and rustls | reuse HTTP/2, system proxies and TLS verification while retaining explicit redirect checks | [network](../architecture/network.md) |
| sign S3 requests in the crate, on `hmac` and `sha2` | a GET needs about a hundred lines of AWS signature version 4, checked against AWS's published examples; the AWS SDK and the other signing crates bring their own HTTP stacks, many more crates or licenses outside deny.toml | [network](../architecture/network.md#trust-boundaries) |
| ask the installed az cli for an azure storage token when no SAS or key covers a listed container, as `AZURE_TOKEN_CREDENTIALS` allows | `az account get-access-token` is azure's own way to hand a login's token to another program, as `export-credentials` is AWS's. its login caches, tenants and second sign-in steps change with the az cli, and reading them here would need azure's libraries. the az cli runs as a `credential_process` does, found only in a folder PATH names in full, and `AZURE_TOKEN_CREDENTIALS` names the sign-in as it does for azure's libraries, so fetchloom never signs in as someone the person's other azure tools would not | [the az cli's login](../../user/guides/private-cloud-storage.md#the-az-clis-login) |
| ask this machine's managed identity for an azure storage token only when `AZURE_TOKEN_CREDENTIALS` names it, through a client of its own | the instance metadata service answers plain http on a link-local address, which the network refuses for every link, since a cloned project could point one at it. so a person's environment turns the identity on, as it chooses an AWS profile, and the one request goes with no proxy, redirect or other credential; trusting the address for the run would let data.toml and data.lock reach it too | [a managed identity](../../user/guides/private-cloud-storage.md#a-managed-identity) |
| say whether the az cli is signed in, for `fetchloom auth`, from the subscriptions its `azureProfile.json` lists | `auth` runs nothing, and an az cli on PATH would otherwise count as a login on every machine that ships one, as CI runners do. the profile names the accounts `az login` saved and their users, but holds no token: fetchloom never reads the az cli's token cache, and a run asks the az cli itself, whatever the profile says | [auth](../../user/commands/auth.md#status) |
| ask the installed AWS CLI for the keys of a profile that signs in to IAM identity center or takes on a role | `aws configure export-credentials` is AWS's own way to hand those keys to another program. sign-in caches, role chains and second sign-in steps change with the CLI, and reading them here would need the AWS SDK or a copy of its rules. a `credential_process` runs as AWS defines it, with no shell, and a profile is never passed over for another identity | [signing private S3 buckets](../architecture/sources.md#signing-private-s3-buckets) |
| keep a key `auth login` saves in the system's credential store, through `keyring`, unless the source's own tools keep a file | windows credential manager, the macos keychain and the linux secret service keep keys out of plain files, and a person manages them with the system's own tools; a machine without a store asks before writing a private file. the price is build time on linux: keyring's secret service store brings zbus, 53 crates no other dependency needs, which with the syn 2 and tracing-attributes only zbus pulls in took 182 of 604 CPU-seconds, about 30%, of a cold debug build at 3 jobs at 89cc7ca6. the other linux stores cost more elsewhere: the dbus store links libdbus, which the static musl build cannot, and the kernel's keyring forgets keys at a reboot. revisit if keyring-core gains a store that runs on tokio alone | [auth](../../user/commands/auth.md) |
| keep disk writes and hashing off async workers | overlap byte processing without blocking request scheduling; bound queues to control retained work | [download pipeline](../architecture/downloads.md#download-pipeline) |
| overlap a required MD5 with SHA-256 when a download has a spare CPU slot | the two checksums together limited a fast download to about 0.37 GB/s; a checked 512 MiB download took 0.77 of the time on two lanes. shared immutable batches stay bounded, checkpoints and cancellation join both, and readback rejoins them to avoid another disk read | [paired checksums](../performance/measurements/archives-and-hashing.md#overlapping-required-checksums-2026-11-12) |
| size verification work by bytes as well as file count | a few large placed files left CPUs idle under the 64-files-per-worker rule. the byte-aware runner keeps the same ordered results, racy-file exclusions and thread-start fallback; low ceilings preserve the old read-buffer count | [verification workers](../architecture/placing.md#verification-workers) |
| reuse archive writers to overlap decoding with large-member hashing | a bounded reusable-buffer handoff lets the decoder advance while an existing writer writes and hashes. short members do not repay the handoff, so their declared size chooses the original path; actual bytes still pass every guard, and cancellation joins writers before cleanup | [archive handoffs](../performance/measurements/archives-and-hashing.md#overlapping-archive-decoding-and-storage-2026-11-12) |
