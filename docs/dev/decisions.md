# decisions

these choices keep byte identity, recoverable storage and the command interface consistent across platforms.

## purpose

research code can outlive the dataset version it used. keep input identities beside that code so collaborators can retrieve the same published bytes without repeating browser downloads and folder renames. a lock cannot restore bytes that every host and cache has lost; long-term preservation still requires someone to retain the data.

## implementation

| what | why | implementation |
|---|---|---|
| keep one rust crate | modules provide boundaries without separate package versions; split only when an independent consumer needs one | [architecture](architecture/README.md) |
| ship one executable, `fetchloom`, and give it the short name `fl` by a link beside it, never in place of another `fl` | a link follows every upgrade and needs nothing more downloaded, so it cannot fall behind, and messages, docs and scripts keep the one name `fetchloom`. the windows installer makes its hardlink again on each install, since a hardlink keeps the old bytes, and the wheel, which can hold no link, runs a python launcher. powershell runs its `fl` alias for `Format-List` before any program, so there `fl.exe` or the user's own alias gives the short name | [installers](engineering/releasing.md#installers) |
| keep adapters in the crate | version, checksum and paging rules stay beside their tests; there is no current plugin-protocol consumer | [sources](architecture/sources.md) |
| route DOIs through the registered handle URL | DOI prefixes and landing-page redirects do not reliably identify the repository | [source routing](architecture/sources.md#parse-before-resolving) |
| support shared-link sources alongside repositories | research inputs also arrive through hugging face, kaggle, drive and dropbox | [source behavior](../user/sources/README.md) |
| use reqwest, tokio and rustls | reuse HTTP/2, system proxies and TLS verification while retaining explicit redirect checks | [network](architecture/network.md) |
| sign S3 requests in the crate, on `hmac` and `sha2` | a GET needs about a hundred lines of AWS signature version 4, checked against AWS's published examples; the AWS SDK and the other signing crates bring their own HTTP stacks, many more crates or licenses outside deny.toml | [network](architecture/network.md#trust-boundaries) |
| keep disk writes and hashing off async workers | overlap byte processing without blocking request scheduling; bound queues to control retained work | [download pipeline](architecture/network.md#download-pipeline) |

## project inputs

| what | why | contract |
|---|---|---|
| identify files by SHA-256 and size | different URLs can share an object; moving a URL does not change byte identity | [cache](architecture/cache.md) |
| learn missing hashes from bytes | a source without a usable checksum still needs a checked pin | [sync loop](architecture/sync-loop.md#resolve-only-changed-specifications) |
| store archive member lists outside the lock | the packed-file entry and tree hash keep lock size independent of member count | [data.lock](../user/reference/data-lock.md) |
| choose files inside an archive in data.toml, by their paths inside it, and keep the choice out of the dataset's spec | placing strips an archive's top folder and that rule may change, while the paths inside an archive are pinned by its tree. out of the spec, a members table changes no pin, so editing one needs no network, `sync --locked` passes and nothing resolves again; the archive still unpacks whole, so the tree stays one hash for every project | [member filters](architecture/archives.md#member-filters) |
| choose the files of many archives with one members table under a glob key, where an archive's own key wins and two globs matching one archive are refused | a webdataset of a thousand shards would need a thousand tables, and a shard pinned later would land whole without a word. refusing an overlap, rather than merging tables or picking one, keeps which table an archive takes readable in data.toml | [member filters](architecture/archives.md#member-filters) |
| leave files out with `drop` by writing patterns into data.toml, never by deleting alone | a file deleted by hand comes back at the next sync, and the deletion stays on one machine; a pattern travels with the project, so every clone leaves the file out, and deleting the line brings it back. drop asks no server: a file inside an archive is named by its path in the archive, which the tree pins, and a listed file's pin is rewritten as relocking the same listing pins it. it refuses what would move a kept file or leave a dataset none | [drop](../user/commands/drop.md) |
| select extraction by recognized archive names, then inspect bytes | ordinary research files stored in zip containers must stay whole | [archives](architecture/archives.md#names-choose-candidates-bytes-choose-decoders) |
| reuse resolved references for filter or extraction edits when `ref` is unchanged | retain explicit versions while selection changes; a changed reference or upgrade resolves the requested reference again | [sync loop](architecture/sync-loop.md#resolve-only-changed-specifications) |
| carry a pin over to the name data.toml renames a dataset to, without asking its source | a rename resolved the source again, so a file that changed upstream was pinned anew under the new name, looking like a first pin, and a teammate got bytes the results never used. the old entry answers the new table only when everything that decides its files is the same, and a name with several equal candidates is resolved as before, so the rule never guesses; a recipe's result follows its recipe the same way, since a key holds no recipe's own name | [dataset names](../user/reference/data-toml.md#dataset-names) |
| cap listings before selection | filtering must not hide unbounded source-list work; this is not a total-project size cap | [sources](architecture/sources.md#keep-listing-and-transfer-separate) |
| let datasets share folders, but give each file one dataset | scripts keep reading paths such as `data/train.csv`, and two datasets often split one folder. a file two datasets placed would change whenever either one's pin did, and the state records one dataset per file, so two datasets placing one path clash even with the same bytes | [placing](architecture/placing.md#expand-destinations-first) |
| an import pins bytes, never a path | `ref = "local"` and an empty link: a path would mean nothing on a teammate's machine and would say where a person keeps their files. the cache copies the files, cloning on linux disks that can, since a hardlink would seal the person's file read-only; a clone without the bytes gets them from a copy adopted in the data folder or from `add <folder> --as <name>`, which checks them against data.lock first | [files on this machine](../user/commands/add.md#files-on-this-machine) |
| leave what a system writes into folders by itself out of an import | finder writes `.DS_Store` into any folder a person opens, and a mac writes a `._` file beside each file it copies to a disk not its own, so pinning them would refuse a teammate's supply of the same data from a mac and put that clutter in every clone's data folder. the list holds only names systems write by themselves, never a name a person could mean as data, and the import says what it left out | [add](../user/commands/add.md#files-on-this-machine) |
| treat local state as observations, not byte authority | missing state can recover by hashing files; a broken pin cannot safely be guessed | [project](architecture/project.md#three-records-with-different-authority) |
| stop project discovery at the top of a git repository | data.toml belongs to the repository that commits it; a manifest above would put pins in another history, and a stray one in a home folder would capture every repository below. `-C` names such a project on purpose | [finding the project](../user/reference/project-folder.md#finding-the-project) |
| merge data.toml and data.lock in `fetchloom lock`, with the base from git's conflict lines or its index, and no merge driver | a merge driver needs setup in every clone. two teammates adding datasets conflicted in both files, and resolving them by hand then relocking resolved the other side's dataset again, one request that could pin newer data than the teammate had. a dataset each side changed its own way is a person's choice, so `--yes` and the JSON `fix` never make it. so is a removal on one side of a dataset whose pin the other side changed: a re-import or an upgrade leaves the entry's text alone, so git takes the removal in data.toml by itself and would drop a teammate's new pin unseen | [after a git merge](../user/commands/lock.md#after-a-git-merge) |
| run git only as a reader: of each side of a merge whole, with its base, and of which lists in data.lock.d git has | apart from the steps `fetchloom build` runs, it is the one program fetchloom runs: found outside the project, with no shell, input or network, bounded in output and time. git's conflict lines hold lines git merged by itself, so a side read from them can mix both sides' lines into one pin; the index's stages, or the commits being merged, give each side as its branch wrote it. reading them reads objects, so git runs with `GIT_ALLOW_PROTOCOL` empty, which denies every transport, and with `--no-lazy-fetch` where it knows the option, so no version fetches a missing object; `git ls-files` reads only the index. without git, the sides come from the conflict lines, every dataset the sides disagree on without a base there needs a choice, and nothing names a list a commit would leave out | [merges](architecture/project.md#merges), [lists git has](architecture/project.md#lists-git-has) |
| name a list in data.lock.d by its dataset and content, and name the lists git does not have rather than keep one name | two branches that each rebuild a recipe write two names, so the merge never conflicts inside a list. a new name is a new file, which `git commit -a` leaves out, and a clone of that commit cannot read data.lock; status and every command that writes a list say `git add data.lock.d` while git lacks one, and the clone's error asks for the commit that adds it, never to delete data.lock, which would drop every recipe's pin | [data.lock](../user/reference/data-lock.md#big-datasets) |
| sync named datasets alone, and never record the project as settled after it | a laptop with a cold cache needs one small dataset without downloading a large one, and edits in two datasets may need only one replaced. every other entry in data.lock and every other file stays as it is, data.toml's changes to them included, so a named sync resolves, downloads and removes nothing of theirs. a settled record would let the next plain sync skip what the named one left out | [named datasets](architecture/sync-loop.md#named-datasets) |
| key a recipe's result by the content it reads, its command as written, its code's bytes and its variables, never by a machine's paths, user, time or version | a moved project, a renamed data folder or a renamed recipe then keeps its key, and a recipe made from another takes that one's result tree, so a rebuild giving the same files changes nothing after it, the early cutoff bazel's action keys and nix's content-addressed derivations rely on. a key that cannot be made, as for missing code, means a build, never a guessed key, unlike the random fingerprint hugging face datasets falls back to | [recipes](architecture/recipes.md#the-key) |
| hash a recipe's text code with each CRLF made LF, as git's text test sees text | git for windows checks files out with CRLF by default, so a linux and a windows clone of one commit would key every recipe apart; a file with a NUL in its first 8,000 bytes is hashed as it is | [recipes](architecture/recipes.md#the-key) |
| take a recipe's `run` as a list of words, never a shell line | a shell would expand, split and quote a cloned repository's text in ways a dry run cannot show; one word stays one argument, spaces and all, on every system | [recipes](../user/recipes.md#declare-a-recipe) |
| find a windows step's program as cmd.exe would, then hand std its full path | std looks in fetchloom.exe's own folder and the windows folders before `PATH` and adds `.exe` alone, so `npm` would miss `npm.cmd` and a program beside fetchloom.exe would stand in for the person's. std keeps quoting a `.bat` or `.cmd` program's arguments and refusing those cmd.exe would misread, which a quoting of our own could get wrong | [recipes](architecture/recipes.md#the-step) |
| run a step with everything it starts in one group fetchloom ends whole: a process group on unix, a job object from process-wrap's tokio wrapper on windows | a process a step left running could write into its result while it is taken in. only that wrapper, with `KillOnDrop`, sets the job's kill-on-close limit, so the job also ends with fetchloom however fetchloom ends; the std wrapper's job would outlive it | [recipes](architecture/recipes.md#the-step) |
| run a recipe only in `fetchloom build`, with no trust database, and never as a JSON `fix` | a recipe is the repository's code running as you; a person reads the commands a dry run shows and builds on purpose. a list of trusted repositories would only move that decision somewhere nobody reads | [recipes](architecture/recipes.md#trust) |
| let a dry run or status count a data folder file unread only where the state vouches for it, by a record of the pinned bytes and a look unchanged since, from before the state was written, and hash any other first | a dry run must never promise what the run will not do: counted by its size alone, an edit of the pinned size, as one made through a hardlink `cp -a` kept, passed for the pinned file, and push's dry run promised a copy the push then refused. it is the rule sync lives by, so a copy whose `.fetchloom` came along costs no read, and one without it is read once | [copies from the data folder](architecture/cache.md#copies-from-the-data-folder) |
| give a step private copies of what it reads, made from the cache's objects, never hardlinks and never the data folder | a hardlink would let a step that writes an input change the cache and every project sharing it, and the data folder holds whatever a person edited, which the key does not answer. a file the cache took from the data folder hashed to its pin first, so the step still reads only pinned bytes | [recipes](architecture/recipes.md#the-step) |
| write data.lock once, after every step a build takes, and keep each finished result in the cache by its key | a failed or stopped step must leave every pin and placement as it was, and a build run again must not run the steps that already worked | [recipes](architecture/recipes.md#committing) |
| move a captured file into the cache only when it has one name and is the user's, and copy any other | a step may link a person's own file into its result, and sealing that file read-only, or making it the cache's object, would change it under them | [recipes](architecture/recipes.md#taking-in-a-result) |
| refuse a result name any supported disk cannot store, and two names one disk takes for one | a result made on linux must place on a teammate's windows or mac, and the place to rename is the step, not every machine after it | [recipes](architecture/recipes.md#taking-in-a-result) |
| keep the files data.lock pins for an unchanged key, even when a rebuild makes others | a step that is not reproducible would otherwise move every clone's pin each time someone builds; choosing the new files is a person's decision | [recipes](architecture/recipes.md#deciding-a-step) |
| check a recipe by running every step from the inputs data.lock pins and comparing with the listing data.lock and data.lock.d commit, reporting every step | a reviewer or a CI runner needs no pinned result on the machine, and a step checked against the pinned result it reads, not another step's rebuild, shows which step is not reproducible rather than every step after it | [recipes](architecture/recipes.md#checking) |
| take the space a build leaves free, `build_floor`, from the settings file or its variable only | data.toml comes with whatever repository a person clones, so a limit it set could let a step fill the person's disk; the default, the larger of 1 GiB and 1% of the disk, keeps room for the rest of the system | [recipes](architecture/recipes.md#the-step) |
| keep a rebuild that differs in the project's state, never as a result record, and pin it only with `build --accept` | a record under `builds/` is what a build reuses, so a kept rebuild there would become a pin without anyone choosing it; the state is the project's own, and gc reads it, so the files stay until someone decides | [recipes](architecture/recipes.md#a-rebuild-that-differs) |
| leave a pinned result that is in no cache or mirror out of a sync of every dataset with a warning, and fail `sync <recipe>` and `sync --locked` with `build.needed`, rather than build it | only `fetchloom build` runs the project's code; a fresh clone still gets its fetched datasets, a script that asks for the result or a locked check fails loudly, and an older pin's files retire so no script reads a stale result | [recipes](architecture/recipes.md#placing-results) |
| let `place = false` only take placement away | data.toml comes with whatever repository a person clones, so a key it holds may keep files out of the data folder, never put them anywhere else; the dataset stays pinned and cached, since recipes read it | [recipes](architecture/recipes.md#placing-results) |
| place a changed recipe's pinned result and warn, every sync and path | the result data.lock pins is what a teammate on the same commit gets, and only a build replaces it; a settled sync that said nothing about edited code let a person read a result their code no longer makes | [recipes](architecture/recipes.md#placing-results) |
| let a sync or path of a recipe read, never fetch, what the recipe is made from | the scope of a named run is exactly its names, so a laptop asking for one result downloads nothing else; the inputs' pins and data.toml entries are already on disk and are enough to say an input moved | [sync loop](architecture/sync-loop.md#named-datasets) |
| keep every file a project needs through gc, and tell apart only what builds alone read | an input of a built recipe is what `cache gc --inputs` frees, where a folder mirror holds a copy it can come back from; until then a pinned input is as needed as a placed file, and a recipe still to build keeps its inputs out of reach of any freeing | [cache](architecture/cache.md#uses-of-needed-objects) |
| let status settle a project as sync does | after a move and `cache gc --now`, status listed every archive member as extra while sync, rightly, found nothing to do; one rule for both keeps status saying what sync would do | [settled-sync shortcut](architecture/sync-loop.md#settled-sync-shortcut) |

mutable URLs and OSF nodes cannot preserve an old listing through a filter edit. review lock diffs because new selections can include newer files; recorded hashes still pin the selected bytes.

## storage and requests

| what | why | invariant |
|---|---|---|
| try reflink, hardlink, then copy; read-only windows placement tries hardlinks first | reflinks isolate later writes; hardlinks share bytes and can reuse a windows scan; copies work when links fail. symlinks can dangle after cache cleanup and need extra windows privileges | [placing](architecture/placing.md#choose-a-filesystem-method) |
| publish a cache object by a link or a rename that refuses a taken name, and by a plain rename only on a disk with neither | a check before a rename that replaces let another writer's object, published between the two, lose its name; FAT and exFAT have no links, but linux, macos and windows can rename on them without replacing. a disk with no such rename still works: the object's name is its verified SHA-256, so a replacing rename swaps identical bytes, and refusing the disk would gain no safety. a person's files never get a replacing rename | [cache publication](architecture/cache.md#publication-and-repair) |
| separate object publication from partial ownership | hardlink publication avoids serializing publishers on one exclusive cache lock; unfinished bytes need an ownership lock, and the shared gc lock protects active runs | [cache publication](architecture/cache.md#publication-and-repair) |
| open cache hashing and copy inputs without following final links | a replaced object name must not redirect these readers to another file | [cache access](architecture/cache.md#safe-object-access) |
| date each object by its birth when sealing it | an edit through a placed hardlink changes the cache's copy behind fetchloom's back; a modification time moved past the birth time puts the object in doubt with one stat and no per-object record, as pnpm's recorded check time does for its store. the date lands just past the file's making, which an nfs 4.2 server with delegated timestamps keeps | [cache access](architecture/cache.md#safe-object-access) |
| keep a link's changed copy beside the pinned file sync puts back | an edit made in place through a writable hardlink changes the cache's copy every project shares, so sync must put the pinned bytes back; scripts such as pandas' `to_csv` write in place, so dropping the changed copy lost real work. a second name for the same file costs no bytes, and a name already taken is refused, never replaced. a copy other projects' links still share is cloned or copied instead, since one shared `.changed` file let an edit in one project change another's; on a disk without clones that costs one copy a project, in this repair only | [local changes](../user/commands/sync.md#local-changes) |
| flush a run of up to 64 files one by one, and a larger one with one `syncfs` | `syncfs` also waits for everything other programs wrote to the filesystem, which took seconds on a busy disk; one by one cost an idle disk under 10 ms more for 64 files, and one large file the same either way | [batch durability](architecture/network.md#batch-durability) |
| flush copied payloads before sync writes state | state must not vouch for bytes still pending write-back; linux batching avoids one flush per small copy | [copy durability](architecture/placing.md#copy-durability) |
| leave checkpoint and lookup indexes as unflushed hints | losing a hint costs resumption or revalidation, while payload identity remains checked | [cache checkpoints](architecture/cache.md#partial-ownership-and-checkpoints) |
| give the other catalogs 10 s once one search catalog has answered | one failing catalog held the dataset picker for 76 s while the others had answered; a slow network still gets unlimited time for the first answer | [search](../user/commands/search.md) |
| ask S3 without a key first, and sign only for buckets `s3_buckets` lists | a public bucket never sees a key, and a cloned data.toml cannot make fetchloom present a key to a bucket of its choosing; a bucket's owner can log the key id of any signed request | [private S3 buckets](../user/sources/buckets.md#private-s3-buckets) |
| take mirrors from the settings, `FETCHLOOM_MIRRORS` and `--mirror`, never from data.toml or data.lock | a cloned project is untrusted: a mirror named there would send requests, and the hashes asked for, to a host nobody chose | [mirrors](../user/mirrors.md#naming-mirrors) |
| ask the cache, then the data folder, then each mirror in order, then the source | a lab disk is closer than the internet and a dead source costs timeouts; a pinned hash lets a mirror withhold bytes but never change them, as nix lets content-addressed paths in without a signature | [mirrors](../user/mirrors.md) |
| take a pinned object the cache lacks from a file the data folder holds at a path data.lock places it at, cloned or copied into the cache and kept only when it hashes to the pin, before any mirror | a project copied with its data folder to a machine whose cache never held its files was a dead end: push said to sync, sync found every file in place and fetched nothing, and an offline build could not read inputs the folder held. the paths come from data.lock's plan, so `.fetchloom/state` need not come along; a link would let a later edit of the file reach the cache, and a file that hashes otherwise is an edit, so it is never taken or changed and the run goes on as it would without it. one seam, `fetch::mirrors::fill`, serves sync, a step's inputs and pinned results, and push asks the same `DataFolder` | [copies from the data folder](architecture/cache.md#copies-from-the-data-folder) |
| copy a mirror's file into the cache, cloned where the disk can, and check it there; never link or rename it | a link would let a later edit on the nas reach every project, and a check of the mirror's file rather than the copy would let a change between the two through | [copies from mirrors](architecture/cache.md#copies-from-mirrors) |
| tell a mirror by a `fetchloom-mirror` file, and skip one without it for the run after one warning | an unmounted network disk leaves an empty folder; one warning instead of one miss per file keeps a run of 100,000 files readable | [mirrors](../user/mirrors.md#what-goes-wrong) |
| ask a web mirror for its marker once a run, and skip one that fails | a dead mirror asked for every file would cost each file a timeout and its retries; go's module proxies are skipped on any answer but 404 and 410 the same way | [network](architecture/network.md#trust-boundaries) |
| in mirror-only mode, let a request go only as a mirror's and only below a mirror's address, checked on every hop before any lookup | a source or a redirect could name a mirror's host on another port or path; the purpose and the address together keep every other request in, search and key checks included. it is a promise, not a firewall, since a person can turn it off | [network](architecture/network.md#trust-boundaries) |
| write mirrors with `push` into folders only | a lab nas, a network share and a usb drive cover labs and air gaps. a server or a bucket gets the folder through a copying tool such as rclone, so fetchloom needs no upload protocols or keys | [push](../user/commands/push.md#where-it-writes) |
| check each pushed file by its hash as it is written and again as read back from the disk, and name it with a rename that never replaces | a mirror can outlive the machine that pushed and be a reviewer's only copy, so a write the disk lost must not take a name; two pushes at once then need no lock, since a name holds one checked copy or none | [publication into mirrors](architecture/cache.md#pushes-into-folder-mirrors) |
| flush the files a push writes together, by the cache's batch rule, then read each back and name it | flushing each file before reading it back made the disk wait once a file: 10,000 small files took 36.7 s on a busy ext4 disk, and 2.7 s together, 0.074 of the time; 100 files of 10 MiB took 0.619, and one 1 GiB file, flushed alone either way, 0.988. a name still points only at bytes read back from the disk | [measurements](performance/measurements.md#pushing-into-a-folder-mirror-2026-11-11) |
| take a pushed file that comes back with a new number, when its owner and size are those of the file written, once made read-only, flushed again and read back | smb mounted with `noserverino` and sshfs without `use_ino` give a file a new number once they forget it, which stopped large pushes for nothing on the lab disks people push to. the owner check keeps out a file another account could change once named, and the flush and read-back keep a name on flushed, checked bytes. the owner compared is the file's as written rather than the running account, since sshfs without `idmap=user` and smb mounted with another `uid=` show another number for the account's own files | [publication into mirrors](architecture/cache.md#pushes-into-folder-mirrors) |
| report a pushed file that something replaced as `local.io`, apart from bytes that read back changed | changed bytes point at the disk and stay `integrity.mismatch`, exit 30. another account's file, one of another size, or on windows any with a new number points at another program writing into the mirror's folder, such as a sync client, a backup tool or antivirus, so its message names that and what to stop, with exit 50 | [push](../user/commands/push.md#common-mistakes) |
| take a file already on a mirror after one look at its name and size | every reader checks each file against its pin anyway, and hashing every copy would read the whole mirror on each push, 1 TB for 1 TB there. a copy of another size, a link or a folder in a file's place is replaced; one with other bytes of the same size is never used, and `sync` names it | [push](../user/commands/push.md#what-it-writes) |
| ask before pushing data whose source wanted an account or accepted terms, or did not say, and never through `--json`'s `fix` | anyone who reads the mirror gets the files without either. `access` is a hint from the source, not a licence check, so only a person may decide who may have the data | [push](../user/commands/push.md#data-you-may-not-share) |
| free raw input with `cache gc --inputs` only where a folder mirror holds a copy that hashes to its name in the same run, and only after a person's yes | a link is no archive and a source can vanish, so the copy a later build takes must be there and whole now; push takes a copy already there after one look, so gc reads each one itself. a web mirror is usually a folder pushed elsewhere, and reading it whole would be a long download. a source that lists the pinned hash waits on the [roadmap](roadmap.md). git-annex likewise refuses to drop what it cannot find elsewhere | [cache](architecture/cache.md#freeing-raw-input) |
| free raw input only, never a recipe's result that only builds read | every build puts back a pinned result the cache lacks, from a mirror or by running its recipe, so freeing one would last only until the next `fetchloom build`, and meanwhile the inputs its recipe reads would turn pending | [cache](architecture/cache.md#freeing-raw-input) |
| read the mirror's copies and ask before taking gc's lock, then walk the needs again under it and look at each copy once more before freeing it | reading 200 GiB of copies takes about half an hour at 120 MB/s, and a question can wait longer; holding the lock every other run waits on through both would stop a shared cache. the walk under the lock and the look at each copy's size and time keep every freed file raw input nothing else keeps, with a copy that is still the one that hashed | [cache](architecture/cache.md#freeing-raw-input) |
| trust a web mirror's origin, as a typed link's | a person named it, as they type a link, and a lab server is usually on a private address; a project cannot name one. trusting its whole host let data.lock links to other ports of it through | [mirrors](../user/mirrors.md#a-web-mirror) |
| send requests to trusted origins through clients of their own, rather than refuse a trusted host's other origins | a resolver sees a name, not a port, so only a client of its own lets a trusted origin reach a private address while its host's other origins reach public ones alone. refusing those origins outright stopped a typed http link that its site sends on to https, which the same link untyped follows | [trust boundaries](architecture/network.md#trust-boundaries) |
| ask a bucket that refused one old version for its objects as they are now first, for the rest of the run | a public bucket that grants no `s3:GetObjectVersion` refuses every pinned version, so 100,000 files paid 100,000 refused requests on every run. the pinned SHA-256 still decides, and a file whose object changed asks for its version after all. a 404 says one version is gone, so it changes nothing for other files | [resumption](architecture/network.md#resumption-and-revalidation) |
| reuse a bucket object whose listing gives the strong ETag and size this machine's URL record holds for its link, instead of downloading it to learn whether it changed | an upgrade of an s3-compatible prefix, whose ETags are no MD5, downloaded every pinned object again to find one new one. the record stays in the cache, not data.lock, so a machine without it downloads as before. a service that keeps an ETag while the bytes change gets the old pin, as a 304 answer would give it, and the bytes' pinned SHA-256 refuses them wherever they are downloaded | [buckets](../user/sources/buckets.md#pins) |
| limit silence instead of total download time | a large transfer that keeps producing bytes can finish | [request policy](architecture/network.md#request-policy) |
| begin adaptive downloads with one stream and split after it proves slow | extra connections slowed fast transfers and helped constrained ones | [network measurements](performance/measurements.md#network) |

| leave transparent huge pages to the system and the allocator | turning them off cut peak memory to 0.33 to 0.73 of what it was, but 4 KiB pages fault far more often: a no-op sync took 1.09 times as long and placing 100,000 files from the cache 1.13 times | [measurements](performance/measurements.md#ab-passes-on-placement-and-startup-2026-11) |
| size a hashing read's buffer to the file, up to 1 MiB | zeroing 1 MiB for every small file cost more than hashing it: importing 100,000 files took 0.81 of the time on the static build and `cache verify` of 100,000 objects 0.78 | [measurements](performance/measurements.md#ab-passes-from-a-profile-of-nine-jobs-2026-11-12) |
| start hashing read buffers at a page | a kernel copies into a buffer 16 bytes past a page, where glibc's allocator puts a large one, several times slower on some cpus: `cache verify` of 8 GiB took 0.70 of the time on glibc | [measurements](performance/measurements.md#ab-passes-from-a-profile-of-nine-jobs-2026-11-12) |
| start the disk on a large download while it arrives, and keep the closing flush | a 10 GiB download flushed every byte after the last one arrived; starting write-back of each 32 MiB after the first 64 MiB made `get -o` take 0.53 of the time, while the closing flush still decides what is durable | [measurements](performance/measurements.md#ab-passes-from-a-profile-of-nine-jobs-2026-11-12) |
| put all archive decoders behind one guard | entry types, paths and expansion limits must agree before members become reusable | [archives](architecture/archives.md#validate-before-publication) |
| read 7z with sevenz-rust2's decoders, leaving ppmd out | it bounds header memory, checks crcs and shares the bzip2, zstd and flate2 crates fetchloom already uses. its `deflate` feature turns on flate2's default features: miniz_oxide, adler2 and simd-adler32 compile though zlib-rs stays the backend, and zlib-rs may pick avx2 code at run time. ppmd-rust is licensed `CC0-1.0 OR MIT-0`, outside deny.toml, so a 7z of ppmd data is refused; allowing `MIT-0` is the owner's call once a dataset needs it | [archives](architecture/archives.md#names-choose-candidates-bytes-choose-decoders) |
| leave rar packed, and name unrar on linux, unar on macos and 7-Zip on windows in its warning | rars 0.12.4, a pure-rust decoder, missed the spike's bar, and the c++ unRAR stays out of the process. macos's `tar` and windows' `tar.exe` need no install, but they are libarchive builds, whose [formats page](https://github.com/libarchive/libarchive/blob/master/libarchive/libarchive-formats.5) promises "limited support" and its [library page](https://github.com/libarchive/libarchive/blob/master/libarchive/libarchive.3) "RAR and most RAR5 archives", with no word on solid ones, and [microsoft's page for tar](https://learn.microsoft.com/en-us/windows/tar/) lists `.tar`, `.tar.gz`, `.zip` and `.7z`. the flags come from [unar's manual](https://manpages.debian.org/unstable/unar/unar.1.en.html) (`-o`, and `-D` for no extra folder) and [7-Zip's help](https://7-zip.opensource.jp/chm/cmdline/switches/output_dir.htm) (`-o` with no space), whose [history](https://www.7-zip.org/history.txt) added rar5 in 15.06; [winget's manifest](https://github.com/microsoft/winget-pkgs/tree/master/manifests/7/7zip/7zip) installs to `%ProgramFiles%\7-Zip`, off the path, and powershell runs a quoted path only after the [call operator](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_operators#call-operator-) `&`. unar 1.10.8 and 7-Zip 26.06 unpacked a solid rar5 and a rar 2.9 sample from libarchive's tests to the same bytes as libarchive 3.7.2. on the rar spike's fixtures, unrar 7.00, rarlab's free reader and the spike's oracle, read solid rar5, rar4 and rar2, rar5 delta and x86 filters and rar5 volumes, where libarchive 3.7.2 refused all but the solid rar5, and ubuntu 24.04's unar 1.10.1 failed a solid rar5, so linux gets unrar: it is free to use, packaged by ubuntu, debian, rpm fusion and arch, and needs one command | [archives](architecture/archives.md#names-choose-candidates-bytes-choose-decoders) |
| hint `--no-extract` before downloading numbered tar shards, and still drop each archive once its files are in | webdataset loaders read shards packed, and unpacked, a shard set becomes a file for every sample, each taking an inode a cluster's quota counts. keeping the archives as well would double the disk, so the hint comes once the listing is known and before anything downloads, while the choice costs nothing. a question, as for a large download, would protect better at 1,000 shards or more, but would also stop runs nobody watches, so it waits for evidence from use | [archives](architecture/archives.md#the-shard-hint) |
| join an archive cut into parts by `split` or 7-Zip when one dataset lists every part, and pin the parts as files with `unpacks_to` on the first | the parts read in order are the archive, so no decoder or lock field is new, and the names already say which files belong together: a `joins` list would repeat them in data.lock and its lists. a set stays inside one folder of one dataset, starts at a first part and follows `split`'s and 7-Zip's numbering, GNU split's `9000` after `89` included; members tables and `drop` name it by that first part | [archives](architecture/archives.md#split-archives) |
| key a split archive's record by every part, and read the parts where the cache keeps them | a record keyed by the first part would hand a changed later part the files its old bytes held. reading part after part with one file open needs no joined copy: a 2 GiB zip in 20 parts unpacked at 25 MiB peak memory against 24 MiB whole, with one part file open | [archives](architecture/archives.md#split-archives) |
| leave a lone first part packed with a warning when its bytes do not unpack, while a pinned set that fails still fails | a first part alone, as `add -i` makes of a list with a link for each part, may be only the start of an archive whose other parts sit in other datasets; failing would stop the add over what a warning explains, and a set whose tree data.lock pins must unpack to it | [archives](architecture/archives.md#split-archives) |
| leave rar volumes and spanned zips packed, with one next step each | only their own tools join them: unrar and 7-Zip read every rar volume from the first, Info-ZIP's [`zip -s 0`](https://linux.die.net/man/1/zip) joins a spanned zip for unzip, and 7-Zip reads spanned zips since [16.02](https://www.7-zip.org/history.txt); unrar 7.00, zip 3.0 and 7-Zip 23.01 did each on linux | [archives](architecture/archives.md#split-archives) |
| unpack an archive left packed into a folder beside it, inside the data folder | fetchloom's `.gitignore` names the data folder alone, so a folder at the project's top went into git with a `git add .`; inside, sync keeps the files as a person's own and `status` lists them as extra. `get`'s help keeps the folder beside the one get fills, which a later `get` refuses once it holds other files | [archives](architecture/archives.md#names-choose-candidates-bytes-choose-decoders) |
| preserve edits and recheck before replacement | files can change while downloads run; interruption recovery must not erase unrelated work | [placing](architecture/placing.md#choose-an-action) |
| write `get -o` by moving a checked download nothing else needs out of the cache, else as a writable clone or copy of the checked bytes, then drop the cache's copy unless a project pins it | the person edits that file, so no other name may share its bytes, and a one-off left in the cache as well would take its space twice. a finished object has one name unless a project linked it, so moving it costs no copy: on ext4, a 2 GiB one-off took 30 s instead of 64 s and wrote 2 GiB instead of 4 (median of five interleaved runs). a move needs one disk and a count of the object's names, which unix gives and windows does not without unsafe calls; a second name, another disk or windows falls back to the clone or copy. the file takes its name without replacing anything, so a file that appeared meanwhile stays and the object goes back to the cache. renaming the unfinished download into place would spare the cache entirely, but every download would then need a second way to finish outside it | [get](../user/commands/get.md#one-file) |
| keep what `--force` replaces until the pinned file is in place | removing an edit before placing lost both the edit and the pinned file when placing then failed; a rename aside keeps the bytes, and the same holds for a changed cache object on a drive that cannot rename over it | [placing](architecture/placing.md#choose-a-filesystem-method) |
| link a file found holding the pinned bytes to the cache's copy | adopting a hand-downloaded file kept it beside the downloaded object, two copies, writable in a read-only dataset; a hardlink keeps one. it is made under a hidden name and renamed over the file only while the file looks as scanned, so the bytes stay until the link has the name | [placing](architecture/placing.md#choose-an-action) |
| report cache space in payload bytes, and count what another name keeps as freeing nothing | gc counts what files hold, while `du` adds whole blocks and folders, so payload is the number a report and gc can share. gc removes an unneeded object a `get` folder links, but its bytes stay with that name, so a report promising them would overstate what gc frees. the weekly reminder uses the report's measure, so the two cannot disagree | [cache](../user/commands/cache.md#inspect) |
| count a project's file as a copy of a cached one only while the cache holds its bytes and it looks as placed | a file whose cached copy is gone holds the only copy of its bytes, and an edited file is the person's own: neither takes room twice, and the report's advice to delete a data folder and sync must never point at an edit. a placed hardlink with no other name is the `rsync -a` without -H case, where the project and its cache each hold the bytes. clones count too, since deleting the cache's copy leaves them whole, and the report says how much is clones, which share blocks until changed. one `symlink_metadata` call a file tells all of it, the link count included on unix | [copies and backups](../user/commands/cache.md#copies-and-backups) |

## interface and maintenance

| what | why | contract |
|---|---|---|
| use flags, environment variables and one settings file | a shared machine or a big scratch disk needs settings that last without exported variables. one order for every value, variable then file then machine then default, with `fetchloom settings` showing where each came from, keeps a second source from becoming a precedence puzzle | [settings file](../user/reference/environment.md#settings-file) |
| require an explicit dataset choice | public catalogs can return several plausible matches; `--yes` only approves downloads | [search selection](../user/commands/search.md#choosing-a-dataset) |
| give errors stable kinds | scripts can act without parsing prose | [exit codes](../user/reference/exit-codes.md) |
| leave `fix` empty in a `--locked` run for any command that may write data.lock | `--locked` promises CI that data.lock stays as committed, and a script or agent runs `fix` unread, so a `fetchloom lock` there would pin what the sources serve now and undo the promise. the rule sits in `output::fix`, which `cli::changes_lock` tells which commands write data.lock, so a new error a locked run ends with cannot slip one through; `help` keeps every way on for a person | [JSON output](../user/reference/json-output.md) |
| keep terminal formatting in one renderer | commands share stream routing, prompts, aligned verbs and progress behavior | [output](architecture/output.md) |
| test behavior and work counts without coverage quotas | extra requests, downloads and copies can be detected independently of runner speed | [engineering](engineering/README.md), [performance](performance/README.md) |
| fuzz parsers in their modules | parsers can remain private without a separate fuzzing API | [fuzzing](engineering/fuzzing.md) |
| ship the same executable in wheels | published binary wheels will let pip users receive the same implementation without rust; current source installation still needs it | [releasing](engineering/releasing.md) |
| test and release native arm64 linux and windows | those artifacts need the same behavioral gate as x86_64 | [CI](engineering/ci.md), [release targets](engineering/releasing.md#workflow) |
| test macos on apple silicon and release it for x86_64 and arm64 | apfs clones files, ignores case and keeps unicode composition, so placement and status need their own gate; the intel build runs its installed-artifact journey before merge as well as before release | [CI](engineering/ci.md), [release targets](engineering/releasing.md#workflow) |
| keep reasons near the implementation and update docs with behavior | contributors can check the constraint before changing it | [style](style.md) |
