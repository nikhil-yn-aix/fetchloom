# Common changes

start with one named test in the module, then widen to these filters, from the repository root.

| change | read | tests to run |
|---|---|---|
| add a source | [sources](../architecture/sources.md), `src/source.rs` | `cargo test --locked --lib source::`; `cargo test --locked --test cli get::`; `cargo test --locked --test cli add::`; `cargo test --locked --test cli project::` |
| change output | [output](../architecture/output.md), `src/output.rs` | `cargo test --locked --lib output::`; `cargo test --locked --test cli progress::`; `cargo test --locked --test cli hints::` |
| fix a placement bug | [placing](../architecture/placing.md), `src/cli/sync/place.rs` | `cargo test --locked --lib place::`; `cargo test --locked --test cli placing::`; `cargo test --locked --test cli recovery::` |
| change the network layer | [network](../architecture/network.md), `src/net.rs` | `cargo test --locked --lib net::`; `cargo test --locked --test cli split::`; `cargo test --locked --test cli proxy::`; `cargo test --locked --test cli secrets::` |
| add a CLI option | [CLI](../architecture/cli.md), `src/cli/args.rs` | `cargo test --locked --lib cli::args::`; `cargo test --locked --test cli basics::`; `cargo test --locked --test cli caps::` |

## adding a command

1. add the argument type and `Command` variant in `src/cli/args.rs`, including its `name()` match arm and its arm in `Command::harmless`, which decides whether a script may run it as the JSON `fix` a help names; that match has no `_` arm, so the command does not build until someone decides. a command that may write data.lock also needs its arm in `Command::writes_lock`, and one that moves data or changes what projects need its arm in `spends` or `reminds` in cli.rs, since their `_` arms leave a new command out without a word. put its copyable examples and on-disk effects in the `examples` constants and connect them with `after_help`; `help::examples_first` moves the examples up below the usage lines when the help prints.
2. declare the handler module and add dispatch in `src/cli.rs`. pass shared settings through `Context`, render through `Output`, and return a serializable report through `finish` so errors and JSON keep the same envelope.
3. check `fetchloom help <command>`, `fetchloom help --json` and unknown-topic suggestions. `src/cli/help.rs` discovers command topics and the JSON command list from clap; update its prose only when the concepts change.
4. add argument tests and real-binary scenarios, declaring any new test module in `tests/cli/main.rs`. snapshot help and human output and check JSON, exit codes, offline behavior, cancellation and disk effects where applicable.
5. extend the command list in `tests/cli/unattended.rs` so a pipe left open on stdin cannot make it wait for input. cover choices separately if the command is interactive.
6. add its page under [docs/user/commands](../../user/commands/README.md), link it from that index, the [user guide](../../user/README.md) and the book's [SUMMARY.md](https://github.com/nikhil-yn-aix/fetchloom/blob/main/docs/SUMMARY.md), and update `llms.txt`. document its result and failure payloads in the [JSON reference](../../user/reference/json-output.md).
7. run the owning tests, [review snapshots](../engineering/building-and-testing.md#update-snapshots), then run the full gate.

every command has one name. a name people bring from other tools, such as `install` or `auth status`, is a usage error whose help names the command meant; `habit` in `src/cli/usage.rs` holds them.

a guess at a mistyped command, option, dataset name, path or help topic goes through `meant` in `src/cli/typed.rs`, which repeats the person's own command line with only the mistyped words changed, so a flag such as `--dry-run` stays in what they paste. a line holding a link with a query, a fragment or a login is never repeated, since any of them may carry a secret under a name `mask_query` does not know, and the help then names the command alone. `may_hold_secret` looks for such a link in a whole word, an option's value after `=`, a link attached to a short option and a link pasted wholly percent-encoded. `command_meant` in usage.rs picks a mistyped command with `name::closest`, ignoring case, rather than taking clap's suggestion, which gave `cache` for `seach`, and turns `rm`, `ls` and `version`, which other tools use and no spelling reaches, into `remove`, `list` and `--version`.

## adding an option

put parsing and conflicts in `args.rs`, then pass the value through `Context` or the command's argument type to its owner. keep presentation in `Output`. update the affected [command reference](../../user/commands/README.md) and [environment reference](../../user/reference/environment.md) when behavior changes.

## add an adapter

1. declare the adapter module and a `Reference` variant in `source.rs`. implement identifier parsing and display in the adapter, then wire `Reference::parse`, `Display`, pasted links in `link` and the relevant `known_host` cases. keep `Parsed.file` for file-specific links.
2. wire `resolve_direct` and, for a DOI-capable repository, destination routing in `src/source/doi.rs`. return a checked `Listing`, preserve unavailable entries, bound pagination through `source::Pages`, which refuses a page named again, more pages than `most_files` files need and 100 pages in a row that bring no new entry (a store may pause a listing with empty pages), in the one wording every source's error carries; a walk calls `Pages::begin` for each folder, since an empty folder is one page with nothing in it, and pin the source's version when it offers one.
3. update `fetch_plan` only if transfers need a page diversion or expired-link handler. keep credential origins and redirects in `Net`. a source with an account adds an `Account` in `src/auth.rs`: where its key lives, its header and host, its token page and a check request.
4. choose existing [error kinds](https://github.com/nikhil-yn-aix/fetchloom/blob/main/src/error.rs) for invalid references, refused access, unavailable data and malformed answers. return refusals through `source::refused` or `Error::needs`, so the error names `fetchloom auth login` and a person at a terminal is offered to sign in; with a key for the account on this machine already, the CLI's `with_key_here` says how to check it instead. `net::failure::refusal` offers none for a plain http link, which no key goes to. a source that refuses a name that does not exist as it refuses a private one, as hugging face and kaggle do, uses `Error::needs_or_missing` with the page that shows the name, so the offer says to check the name there before it asks; the offer defaults to no. a source that tells a refused key apart, as the hub's `auth-check` does with a 401 for a request it took as nobody's, names the key by its `Origin` as the network found it, through the environment `source::env` reads, and offers no sign-in for a key from a variable. a malformed answer's help is `error::report_answer`, which sends it to fetchloom's issues at `error::ISSUES`, since only a newer fetchloom can read a service that changed; a listing whose content only the dataset's owner can change, such as a name `source::refused_name` refuses or an OSF file kept outside OSF storage, gets help that names the owner. if a new kind is necessary, update its serialized name, exit mapping and [exit-code reference](../../user/reference/exit-codes.md).
5. add recorded responses under [tests/fixtures/sources](https://github.com/nikhil-yn-aix/fetchloom/tree/main/tests/fixtures/sources) and `Recorded` tests for parsing, display, paging, pins, missing files, access failures and malformed replies. cover command or transfer effects in [CLI tests](https://github.com/nikhil-yn-aix/fetchloom/tree/main/tests/cli). a CLI test runs the real binary, so its requests go to the real host until the host is in the match in `test_source` in `src/net/api.rs`: add every host the source's listings and downloads reach, and the test then sets `FETCHLOOM_TEST_SOURCES` to a local `Routes` server, which a debug build asks at `/<host><path>`, as the [repository tests](https://github.com/nikhil-yn-aix/fetchloom/blob/main/tests/cli/repositories.rs) do.
6. add an ignored live test against a small public record, stating the host in its ignore reason. keep it separate from deterministic recorded coverage.
7. if the source has a public search catalog, add its query and candidate mapping in `src/source/search.rs`, recorded ranking/error tests in `src/source/search/tests.rs`, and update the documented catalog order and [CLI search tests](https://github.com/nikhil-yn-aix/fetchloom/blob/main/tests/cli/search.rs). those tests stand a local server in for each catalog through a variable of its own: add the catalog's API host to `test_endpoint` in net/api.rs with a `FETCHLOOM_TEST_<SITE>_API` name, as `FETCHLOOM_TEST_ZENODO_API` stands in for zenodo.org, and list it with the [debug-only hooks](test-harness.md#debug-only-hooks).
8. add a page under [docs/user/sources](../../user/sources/README.md) with accepted forms, pinning, limits and access rules. link it from that index, the [user guide](../../user/README.md), the book's `docs/SUMMARY.md` and `llms.txt`. name the source and its reference form where every source is listed: the [README](https://github.com/nikhil-yn-aix/fetchloom/blob/main/README.md), the agent skill's `skills/fetchloom/SKILL.md`, the [compatibility](../../user/reference/compatibility.md#sources) table of each source's API and hosts and the [data.lock](../../user/reference/data-lock.md#what-each-source-records) table of reference forms and file links. update [environment settings](../../user/reference/environment.md) for credentials, relevant examples and help text in `src/cli/args.rs` or `src/cli/help.rs`, and the affected help snapshots.

## adding a setting

to add a setting:

1. name its settings-file key and the variable that overrides it in `KEYS` in `src/settings.rs`, which the file reader, `variable` and the typo check `misnamed` read, and add the key to `LISTS`, `BOOLEANS` or `CLEARED` when it holds a list or true or false, or when an empty variable must clear it. a variable without a key goes in `OTHERS`.
2. give `Settings` a `Set` field, its default in `Settings::defaults`, and read it in `Settings::read` with the reader of its kind, such as `count`, `size`, `seconds` or `boolean`, which records where the value came from.
3. when a level derives it, add it to `Limits` in `src/settings/resources.rs`, give each level its value in `Level::limits` and read it in `Settings::read` through `derived`, so a value set by name still wins; a setting no level derives joins the values `the_default_level_keeps_the_defaults_and_no_level_moves_what_it_does_not_derive` compares.
4. add its row to `rows` in `src/cli/settings.rs`, so `fetchloom settings` shows its value and where it came from.
5. describe the variable in `ENVIRONMENT` in `src/cli/help.rs`, within 80 columns, and the key in the list of what a settings file keeps below it.
6. document the variable and the key in the [environment reference](../../user/reference/environment.md), and anything new about its origin in the [settings command](../../user/commands/settings.md) page. `every_setting_is_documented_and_every_documented_one_is_read` in `tests/cli/docs.rs` fails until the reference names a variable the code reads, and `the_environment_topic_names_every_variable_the_docs_do` in cli/help.rs until the help topic names the same ones.
